# GoRangeTask 性能基线

> **本文对应一台 i5-8200Y（4 逻辑核）笔记本，保留作历史证据。**
> 当前开发机（Ryzen 7 8745H / Windows 11 + Docker Desktop）的复测见
> 《[GoRangeTask-性能基线-Ryzen7-8745H.md](./GoRangeTask-性能基线-Ryzen7-8745H.md)》。
> **两套数字不可混用**：本文里"W=4→16 只能拿到 1.4–1.9 倍""MySQL CPU 到顶"等结论是**那台机器**的结论，
> 换机器后不成立；本文 §9 的"可解释上界"也已在新文档中被修正（见该节开头的更正说明）。

> 用途：记录 GoRangeTask 在**一台具体机器、一套具体配置**下的实测数字，以及这些数字能说明什么、不能说明什么。
> 定位：实测报告，不是承诺。所有数字都能追溯到 `bench/results/*.json` 里的原始样本。

## 0. 先看结论

1. **事务完整率 100.00%**：10,000 笔"业务行 + 任务行同一事务"（5,000 提交 / 5,000 回滚）跑完，已提交的 5,000 行业务记录**全部**有对应任务，回滚后残留业务行 0、孤儿任务 0（§8）。这是本项目最核心的那条性质，也是唯一一个"非黑即白"的数字。
2. **崩溃恢复 2.07 s**（租约 2 s / 回收周期 250 ms 的配置下）：Worker 停止续租后，另一个 Worker 在 2.07 s 内把任务接手跑完，恢复时间几乎全部是一个剩余租约；旧执行者解冻后的写回被 fencing 拒绝（§9）。
3. **稳态排队延迟 p95 = 260–500 ms**：这个数由 `PollInterval` 250 ms 与空队列退避决定，**不是**由任务处理决定（Handler 只有 0.03 ms）。积压 1000 条时 p95 是几十秒——那是积压的度量，不是调度的度量（§6.2、§4）。
4. **吞吐随 Worker 并发上升，但不成正比**：256 B payload 下两次运行分别落在 W=1/4/16 = 24–29 / 47–49 / 66–96 task/s。W=1→4 稳定在 1.7–1.9 倍（接近线性），W=4→16 只有 1.4–1.9 倍——4 倍的 Worker 换不来 4 倍的吞吐。瓶颈不在行锁（InnoDB 行锁等待几乎为 0），而在同一索引页上的闩锁争用与 MySQL 进程 CPU。
5. **`SKIP LOCKED` 把行锁等待消掉了**：18 个"场景 × 运行"组合里（9 个排空场景 × 2 次运行），`Innodb_row_lock_waits` 有 14 个为 0，其余 4 个各 1 次、累计 6–8 ms。这是"并发领取不互相阻塞"的直接证据。
6. **每个任务固定 6 条 SQL**：1000 条任务对应约 6004 条语句，且 W=1 与 W=16 几乎相同（6004 vs 6049）——说明高并发下没有额外的重试、回滚或重复领取。
7. **空队列的代价是每 worker 约 2 条 SQL/s**：1/4/16 个 Worker 分别是 1.9 / 8.1 / 31.7 QPS，几乎正比于并发数，与任务量无关。
8. **入队延迟由磁盘 fsync 支配，不是由本库支配**：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` 下，一次提交要落盘，8 个并发 producer 的 p50 就到 27–70 ms。**同一事务里多写一条任务行的边际成本在本机噪声内无法分辨**（两次运行给出 +3.3 ms 与 +30.5 ms 两个互不相容的估计，见 §7）。

**这份文档不能用来声称**：比 RabbitMQ/Redis 快、能支撑每秒多少任务、某个具体延迟上限。原因见 §11 与 §10（同一格吞吐在两次运行间能差 45%）。

## 1. 怎么跑

```bash
# 一条命令跑完整矩阵（会先检查容器是否在跑）
scripts/bench.sh

# 单独跑某个场景
export GOTASK_BENCH_DSN='root:rootpw@tcp(127.0.0.1:3306)/gotask_bench?parseTime=true&loc=UTC&timeout=5s&readTimeout=30s&writeTimeout=30s'
go run ./bench -scenario drain -workers 1,4,16 -sizes 256,4096,32768 -tasks 1000
go run ./bench -scenario latency -workers 1,4 -arrivals 100ms,500ms
go run ./bench -scenario txcheck -txcount 10000
go run ./bench -scenario recovery
```

结果写成 JSON（`-out`），JSON 里带完整环境信息，所以任何一行的数字都能回答"在哪台机器、什么 MySQL 配置下测的"。

几个测量约定，都是为了让数字经得起追问：

- **原始样本不折叠**：每个调用的耗时都留着，分位数用最近秩法（`ceil(p·N)-1`）从原始样本取，不做插值、不用均值反推。
- **分位数不能相减**：两个独立样本的 p95 之差没有统计意义，因此"入队开销"只比较**均值**与吞吐（§7）。
- **计数必须自洽**：每个 drain 场景结束都核对"指标说完成 N 条 = 库里 N 条 `succeeded`"，对不上直接以非零码退出——宁可没有数字，也不要一个"看起来跑完了"的数字。
- **不用轮询干扰测量**：等待排空看的是指标计数，不是每 20 ms 发一条 `COUNT`（那会把"DB 语句数"这一列污染掉）。

## 3. 入队延迟

三种模式，8 个并发 producer，每种 800 次调用：

- `producer_tx_baseline`：只在一个事务里插业务行（`bench_orders`），不碰任务表——这是"没有队列"的基线。
- `producer_tx`：同一个事务里插业务行 + `EnqueueTx`——这是本库推荐用法。
- `enqueue`：单独调 `Enqueue`（自动提交），没有业务事务。

| 模式 | 运行 | 吞吐 (次/s) | p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|
| `producer_tx_baseline` | 1 | 105.8 | 62.8 ms | 130.2 ms | 587.9 ms | 668.4 ms |
| （同上） | 2 | 202.5 | 36.5 ms | 62.4 ms | 76.8 ms | 93.6 ms |
| `producer_tx` | 1 | 101.1 | 70.4 ms | 139.5 ms | 189.3 ms | 211.1 ms |
| （同上） | 2 | 113.9 | 66.6 ms | 105.2 ms | 139.4 ms | 156.1 ms |
| `enqueue` | 1 | 148.0 | 41.0 ms | 104.1 ms | 157.3 ms | 164.6 ms |
| （同上） | 2 | 266.2 | 27.2 ms | 51.9 ms | 68.8 ms | 82.5 ms |

**怎么读这张表**：一次提交要 fsync 两次（redo + binlog），所以 p50 落在几十毫秒。这不是 GoRangeTask 的开销，而是这台机器的磁盘与 `flush_log_at_trx_commit=1` 的组合成本——同一个基线模式下不碰任务表也一样慢。`producer_tx_baseline` 的 p99/max（588/668 ms）明显高于另两组，是两次运行中偶发的 checkpoint 抖动；尾部的绝对值不可外推，只能说明"这台机器上尾延迟会被磁盘事件支配"。

## 4. 吞吐与伸缩

每个场景预置 1000 条任务（用一个事务批量入队，避免把 1000 次 fsync 算进"预置耗时"），然后让 Worker 排空。

（表为第 1 次运行；第 2 次见 §10）

| 并发 | payload | 吞吐 (task/s) | 排空 (s) | claim p50/p95/p99 | 排队 p95 | 处理 p95 |
|---|---|---|---|---|---|---|
| 1 | 256 B | 24.4 | 41.0 | 25.4 / 40.5 / 60.1 ms | 39204 ms | 0.03 ms |
| 4 | 256 B | 47.1 | 21.2 | 51.0 / 78.5 / 99.0 ms | 20521 ms | 0.03 ms |
| 16 | 256 B | 65.9 | 15.2 | 125.0 / 247.8 / 405.2 ms | 14767 ms | 0.03 ms |
| 1 | 4096 B | 21.1 | 47.4 | 26.2 / 60.7 / 87.8 ms | 45691 ms | 0.03 ms |
| 4 | 4096 B | 37.4 | 26.7 | 56.8 / 104.8 / 137.8 ms | 25454 ms | 0.03 ms |
| 16 | 4096 B | 74.2 | 13.5 | 123.0 / 190.8 / 255.4 ms | 13135 ms | 0.03 ms |
| 1 | 32768 B | 14.6 | 68.4 | 31.3 / 92.3 / 120.8 ms | 64194 ms | 0.03 ms |
| 4 | 32768 B | 35.5 | 28.2 | 62.9 / 103.8 / 145.6 ms | 26693 ms | 0.04 ms |
| 16 | 32768 B | 36.9 | 27.1 | 237.9 / 352.0 / 644.9 ms | 27622 ms | 0.03 ms |

**怎么读**：

- **W=1 → W=4 是最划算的一档**（256 B：24.4 → 47.1 即 1.9 倍；4 KB：21.1 → 37.4 即 1.8 倍）：领取是 `FOR UPDATE SKIP LOCKED`，四个消费者互不阻塞，符合预期。
- **W=4 → W=16 明显低于线性**（47.1 → 65.9 与 49.4 → 95.6，即 1.4–1.9 倍）：MySQL 进程 CPU 已经到 93–125%（单核百分比）以上，并且这一格在两次运行间能差 45%（§10）。这台机器只有 4 个逻辑核，还要与压测进程共享，所以这个天花板是**环境的天花板**，不是库的天花板。
- **32 KB payload 时两次运行给出相反结论**（W=4→16：35.5 → 36.9 几乎无增益，26.1 → 50.0 接近翻倍）：这一格的噪声已经超过了要测的效应，不应从中得出"大 payload 不能扩并发"的结论，只能说"大 payload 时并发收益不稳定"。
- **"排队 p95" 在这张表里是积压的度量，不是调度的度量**：1000 条任务排队，最后一个自然要等整队排空。要看调度开销请看 §6（稳态排队延迟）。

## 5. 资源占用与 DB 成本

| 并发 | payload | 锁等待 次/ms | DB 语句数 | 池最高占用 | MySQL CPU 均值/峰值 |
|---|---|---|---|---|---|
| 1 | 256 B | 0 / 0 | 6004 | 1 | 42% / 51% |
| 4 | 256 B | 0 / 0 | 6013 | 4 | 93% / 100% |
| 16 | 256 B | 0 / 0 | 6047 | 16 | 144% / 185% |
| 1 | 4096 B | 0 / 0 | 6004 | 1 | 36% / 58% |
| 4 | 4096 B | 0 / 0 | 6013 | 4 | 68% / 92% |
| 16 | 4096 B | 1 / 8 | 6049 | 16 | 107% / 178% |
| 1 | 32768 B | 0 / 0 | 6004 | 1 | 32% / 50% |
| 4 | 32768 B | 0 / 0 | 6013 | 4 | 84% / 132% |
| 16 | 32768 B | 0 / 0 | 6049 | 16 | 74% / 133% |

**三个可验证的结论**（表为第 1 次运行，第 2 次同形）：

1. **行锁等待几乎为 0**：18 个格子（9 个场景 × 2 次运行）里只有 4 个出现 1 次、累计 6–8 ms。`SKIP LOCKED` 的作用就是把"多个消费者抢同一批行"变成"各拿各的"，这一列是它生效的直接证据。
2. **每个任务 6 条 SQL，且与并发无关**：以第 1 次运行为例，6004（W=1）/ 6013（W=4）/ 6047（W=16）条语句对应 1000 条任务，差值 0.8% 以内（第 2 次运行同形：6004 / 6013 / 6049）。这 6 条是：claim 事务的 `BEGIN + SELECT ... FOR UPDATE SKIP LOCKED + UPDATE ... running + COMMIT`，提交后按主键回读整行的 `SELECT`，以及写回终态的 `UPDATE`。**并发升高不产生额外语句**，意味着没有死锁重试、没有重复领取、没有补偿写入。
3. **连接池占用正好等于 Worker 数**（1 / 4 / 16，池上限 32），`wait_count` 全为 0：池没有成为瓶颈，也没有出现连接泄漏（`max_in_use` 不应随时间上升）。

**一处值得注意的现象**：claim 延迟随并发明显上升（W=1 时 p50 约 21–31 ms，W=16 时 99–238 ms，两次运行一致），而行锁等待又是 0。两者不矛盾——争用发生在**同一个索引页的闩锁**上，而不是行锁上。`SKIP LOCKED` 消除的是"等别人释放行"，消除不了"16 个事务同时摸同一棵 B+ 树的同一页"。这也解释了 W=16 的收益为什么低于线性：消费者不再互相阻塞，但仍然在同一个热点上排队。

## 6. 空队列轮询与稳态排队延迟

### 6.1 空队列轮询的成本

空队列时 Worker 按 250 ms 起步、指数退避到 2 s（带抖动）。跑满 15 秒观测窗口：

| 并发 | 观测窗口 | DB 语句数 | DB QPS | 每 worker QPS | MySQL CPU 均值 |
|---|---|---|---|---|---|
| 1 | 15.0 s | 29 | 1.93 | 1.93 | 1.8% |
| 4 | 15.0 s | 122 | 8.13 | 2.03 | 2.5% |
| 16 | 15.0 s | 476 | 31.72 | 1.98 | 3.6% |

**不要把这里的 QPS 读成"任务/s"**：一次空轮询是 `BEGIN + SELECT + COMMIT` 三条语句，所以 1.93 QPS ≈ 0.64 次轮询/s，与"退避到 2 s 上限"是同一个量级（观测窗口前段还停留在更密的轮询上，所以略高于 0.5）。每 worker 约 2 QPS 且与并发数成正比（1.93 / 2.03 / 1.98），这是一个可以直接用来估算"空转成本"的数：**100 个空闲 Worker 约 200 QPS、MySQL CPU 在个位数百分比**。

### 6.2 稳态排队延迟

方法是"让队列永远不积压"：按固定间隔（100 ms / 500 ms）一条一条入队，Worker 必须跟得上，于是测到的是**从入队到 Handler 开始**的等待，而不是"前面还有多少条"。

任务数由观测窗口（30 s）推出来，所以两个到达间隔的窗口长度一致（200 条 / 60 条），分位数可比。

| 并发 | 入队间隔 | 任务数 | 排队 p50 | 排队 p95 | 排队 p99 | 排队 max | claim p50 | claim p95 |
|---|---|---|---|---|---|---|---|---|
| 1 | 100ms | 200 | 132 ms | 260 ms | 283 ms | 314 ms | 18 ms | 65 ms |
| 4 | 100ms | 200 | 121 ms | 304 ms | 403 ms | 437 ms | 17 ms | 86 ms |
| 1 | 500ms | 60 | 231 ms | 497 ms | 778 ms | 778 ms | 19 ms | 143 ms |
| 4 | 500ms | 60 | 160 ms | 405 ms | 628 ms | 628 ms | 6 ms | 28 ms |

**怎么读**：Handler 什么都不做（处理 p95 只有 0.03–0.05 ms），所以这张表里的等待**全部来自"多久看一次队列"**，也就是 `PollInterval` 250 ms 加上空队列时的指数退避。

- 到达间隔 100 ms 时 p50 是 121–132 ms，约为轮询间隔的一半——符合"均匀分布的到达，平均等半个轮询周期"。
- 到达间隔 500 ms 时 p50 升到 160–231 ms、p99 到 628–778 ms：队列在两次领取之间常常是空的，Worker 已经退避（500 ms → 1 s），下一条任务要等下一次轮询才被发现。**延迟变大的原因不是负载，而是稀疏**。
- **加 Worker 并不能按比例降低这个延迟**（W=4 的 p50 是 121 / 160 ms，相比 W=1 的 132 / 231 ms 只降了 8% / 31%，而不是四分之一）：它不是"处理不过来"造成的，所以加消费者没用。要降低它只能调小 `PollInterval`，代价是空转轮询变密（这一组对照没测，见 §11）。
- 这一组跑在宿主负载 7.81（前）/ 3.62（后）的时段，绝对值比干净机器上偏悲观；可迁移的是**形状**：延迟由轮询参数支配，与队列长度和并发数都弱相关。

## 7. 入队对调用方事务的边际成本

同一事务形状下，多写一条任务行的代价（`producer_tx` 对比 `producer_tx_baseline`）：

| 运行 | baseline 均值 | 含任务行均值 | 差值 | 吞吐 baseline → 含任务行 | 变化 |
|---|---|---|---|---|---|
| 1 | 74.70 ms | 77.97 ms | **+3.27 ms** | 105.8 → 101.1 次/s | −4.4% |
| 2 | 38.87 ms | 69.37 ms | **+30.50 ms** | 202.5 → 113.9 次/s | −43.8% |

**这两次运行给出了互不相容的答案**（+3.3 ms / −4.4% 与 +30.5 ms / −43.8%），所以本机**测不出**这一代价：噪声（磁盘 fsync 抖动、同机其他负载）与被测量的效应同阶，甚至更大。任何"多写一条任务行只要 X ms"的说法在当前环境里都不成立。

要真正测它，得换一种设计——同一个连接上交替执行两种事务形状、固定 fsync 次数、单线程、关掉同机其他负载，用配对差值而不是两组独立样本比较。这属于后续工作，不是本文的结论。

**能说的只有一句**：在这台机器的噪声内，事务内入队没有表现出可测量的额外成本；这不等于"没有成本"，只等于"这里测不出来"。

## 8. 事务完整率

口径（需求 §10.3 要求的是"提交时两者同时存在、回滚时两者同时不存在"，这里把它量化；公式见《STAR》）：已提交业务记录中存在对应任务的记录数 ÷ 已提交业务记录总数。

| 项 | 值 |
|---|---|
| 事务总数 | 10,000（5,000 提交 / 5,000 回滚，严格对半） |
| 并发调用方 | 8 |
| 耗时 | 67.3 s（约 149 笔/s） |
| 已提交业务行 | 5,000 |
| 其中**有对应任务** | 5,000 |
| **事务完整率** | **100.00%** |
| 回滚后残留业务行 | 0 |
| 孤儿任务（有任务行、没有业务行） | 0 |

**为什么这样核对**：只报一个"100%"是不够的，必须同时看到两个 0——否则"回滚后残留业务行"和"入队成功但业务回滚"这两类错误可以互相掩盖成一个漂亮的比例。业务行与任务行靠**幂等键携带业务行主键**（`txcheck-<order_id>`）一一对上，比的是逐行对应关系，不是两侧总数相等。

**这个 100% 说明什么、不说明什么**：它证明"业务行与任务行在同一事务里要么都提交要么都不存在"，也就是本库的卖点成立。它**不**证明 GoRangeTask 比直接在业务代码里写 SQL 更快或更可靠——那是另一个问题，需要对照实验。

## 9. 崩溃恢复耗时

> **2026-10-18 更正**：本节"可解释的上界 2.53 s"这一行**推导是错的**。公式里用了轮询下限
> `PollInterval`（250 ms），但崩溃期间接手方正在空轮询，退避会爬到 `MaxPollInterval`（2 s），
> 所以真实上界是 1.99 + 0.25 + 2.0 + 执行 ≈ **4.29 s**。新机器上连测 5 次得到 2.05–3.68 s，
> 直接顶穿了 2.53 s；`bench/scenarios.go` 已改为按 `MaxPollInterval` 推导。
> 本节 2.07 s 这个**观测值**仍然是真的，但它只是分布的左端，不能读成"接近上界"。
> 详见《[GoRangeTask-性能基线-Ryzen7-8745H.md](./GoRangeTask-性能基线-Ryzen7-8745H.md)》§9。

要回答的问题是"Worker 在持有任务时消失，多久之后任务会被别人接手跑完"。这个时间由三部分构成，而且**可配置**：剩余租约 + 一个回收周期 + 一次轮询（外加领取与执行本身）。

| 项 | 值 |
|---|---|
| 配置 | 租约 2 s / 心跳 666 ms / 回收周期 250 ms / 停机预算 500 ms |
| 停止续租那一刻的剩余租约 | 1982 ms（占满租约 99%） |
| **从停止续租到另一个 Worker 跑完** | **2.07 s** |
| 可解释的上界 | ~~2.53 s~~ → 按修正后的公式应为 4.29 s（见上方更正框） |
| 最终状态 | `succeeded`，`attempt = 2` |
| 两个 Worker 的 Handler 执行次数 | 各 1 次（合计 2 次，即"被领取两次"） |
| 陈旧 Worker 解冻后的写回 | **被拒**（`ErrLeaseLost`，指标记为一次失租） |

**怎么读这个 2.07 s**：它几乎全部是**剩余租约**（1.98 s）——回收器必须等到租约过期才敢把任务交还队列，剩下的 0.09 s 才是"回收周期 + 轮询"的实际等待。所以：

```text
恢复耗时 ≈ 崩溃时剩余的租约 + 最多一个回收周期 + 最多一次轮询
```

崩溃发生得越接近上一次续租，剩余租约越长、恢复越慢；最坏情况就是一个完整租约。这台机器上这次恰好是 99% 满租约，因此 2.07 s 已接近该配置下的上界。**这两个参数（`LeaseDuration` / `ReapInterval`）就是恢复时间的旋钮**，调小它们会更快发现崩溃，代价是续租更频繁（数据库语句更多）。

**为什么不用真的 `kill -9`**：进程消失对数据库留下的痕迹只有两件事——租约不再被延长、也没有人写回。让一个 Handler 无视 ctx 卡住、再取消 Worker 的 `Run`，产品语义恰好产生同样的库侧状态（`Run` 在 `ShutdownTimeout` 后放弃等待并返回 `ErrShutdownTimeout`，续租看护随停机一起停掉），而且完全确定、可重复。代价是那个 Handler 的 goroutine 还活着，所以测量结束时会放行它，并断言它拿着陈旧 epoch 的写回被拒绝——这一条同时是 fencing 的端到端证据。

**"旧 worker 复苏"的完整故障注入**（真子进程 + `SIGSTOP` + 接管 + 解冻 + 整行快照零改动）在 `store/mysql/revival_integration_test.go`，那里验证的是"写回被拒且一个字段都没变"，不是耗时。本节只回答"多久能恢复"。

**一个前提**：回收只在 Worker 进程内跑。如果集群里连一个 Worker 都没有，租约到期不会触发任何动作，任务会一直停在 `running`——这一点在 README 的语义部分有专门说明。

**三条观察**：

1. **空队列 QPS 几乎完全可复现**（1.93 / 1.93、8.13 / 8.33、31.72 / 32.85）：它由配置（轮询间隔、退避上限）决定，与负载无关，是最"硬"的一个数。
2. **吞吐的波动很大**（同一格最坏能差 60%，如 W=16 / 256 B 的 66 与 96）：这台机器同时跑着别的东西（1 分钟负载 2.7–5.8 波动），而吞吐恰好对 CPU 竞争最敏感。**所以本文所有吞吐数字都应读作"这个量级"，不是"这个值"**。
3. **入队延迟波动同样大**（基线模式 105.8 与 202.5 次/s）：fsync 的成本取决于磁盘此刻在做什么。任何拿单次运行结果去比较"优化前后"的做法在这台机器上都是无效的。

## 11. 由此得出的工程结论

- **想提高吞吐，先看两个东西**：MySQL 进程 CPU，以及 claim 延迟随并发的增长。行锁等待为 0 说明问题不在并发控制，而在热点索引页与单机资源。
- **`PollInterval` 是延迟旋钮，但它的成本曲线还没测**：§6.2 显示排队延迟几乎完全由它决定（250 ms → p50 约 130 ms）。调到 50 ms 能把延迟压到同一比例，代价是空队列轮询变密；"延迟降多少 / 空转涨多少"这一组对照没有测，是本基线明确留下的缺口。
- **`BatchSize` 是下一个该测的旋钮**：本次全部用 1（一次领一条）。批量化能摊薄"每个任务 6 条语句"里的 claim 事务部分，但会放大单次事务的锁范围——需要单独测。
- **回收器与清理器的代价没有进本基线**：它们默认开着（30 s / 1 h），一次回收是"加锁读 + 分流写回"的短事务，一次清理是"加锁读 + 批量删"。要在有积压的真实负载下评估，而不是在空转环境里。
