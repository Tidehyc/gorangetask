# GoRangeTask 性能基线（Ryzen 7 8745H / Windows 11 + Docker Desktop）

> 用途：记录 GoRangeTask 在**这台开发机、这套配置**下的实测数字，以及这些数字能说明什么、不能说明什么。
> 定位：实测报告，不是承诺。所有数字都能追溯到 `bench/results/20261018T*.json` 里的原始样本。
>
> **与旧版的关系**：仓库里另有一份《[GoRangeTask-性能基线.md](./GoRangeTask-性能基线.md)》，测的是一台
> i5-8200Y（4 逻辑核）笔记本。两份文档**不可混用**：章节编号与测法相同，结论却不相同——尤其是
> "W=4→16 只能拿到 1.4–1.9 倍"这条，在本文的机器上不成立。对照见 §13。

## 0. 先看结论

1. **事务完整率 100.00%**：10,000 笔"业务行 + 任务行同一事务"（5,000 提交 / 5,000 回滚）在 11.7 s 跑完
   （约 856 笔/s），已提交的 5,000 行业务记录**全部**有对应任务，回滚后残留业务行 0、孤儿任务 0（§8）。
   这条性质与机器无关，是唯一一个"非黑即白"的数字。
2. **吞吐是旧机器的 7–11 倍**：256 B payload、W=1/4/16 = **66 / 251–260 / 676–714 task/s**（两次运行），
   补充测的 W=32 到 **1,000 task/s**。W=1→4 是 3.8–3.9 倍、W=4→16 是 2.7 倍、W=16→32 是 1.4 倍：
   **仍在涨，但每加一个 Worker 的边际产出在下降**（每 worker：66 → 63 → 43 → 31 task/s）。
3. **这台机器没测到库的天花板**：W=16 时 MySQL 进程只用了 **0.9–1.4 个核**（16 线程的机器），
   W=32 时 1.8–2.2 个核；瓶颈不在 MySQL CPU，也不在行锁（§5）。
4. **W=1 的 66 task/s 可以精确解释**：每条任务要**两次持久提交**（claim 一次、终态写回一次），
   这台机器上一次 fsync ≈ 7.5 ms，所以 1000 条 = 1000 × 2 × 7.5 ms ≈ 15.1 s。
   两次运行的这个格子分别是 15.10014 s 与 15.10047 s——差 0.3 ms，因为它由磁盘时钟决定，不由调度决定。
5. **并发靠 group commit 摊薄 fsync**：W=16 时 16 条任务共享同一次落盘，才有 700 task/s；
   但 claim 延迟随之从 10 ms 涨到 14–18 ms（p50），说明同一个索引页上的争用开始出现。
6. **每个任务固定 6 条 SQL**，与并发和 payload 都无关：1000 条任务 → **6004 / 6013 / 6049** 条语句
   （W=32、2000 条任务 → 12097 条，仍是 6.05 条/任务）。没有重试、没有重复领取、没有补偿写入。
7. **行锁等待接近 0 但在高并发下开始出现**：主矩阵 18 个"场景 × 运行"组合里 2 个各 1 次、累计 0 ms
   （都在 W=16 / 32 KB 这一格）；W=32 探针里 1–3 次、累计 2 ms。`SKIP LOCKED` 仍然有效，但"0 次"已不成立。
8. **稳态排队延迟 p95 = 139–414 ms**：与旧机器同量级，由 `PollInterval` 250 ms 与空队列退避决定，
   与 Handler 无关（处理 p95 = 0.00 ms）。加 Worker 能降它，但降不到"除以 Worker 数"。
9. **入队延迟 p50 = 6.0–9.7 ms**（旧机器 27–70 ms）：同样是"每次提交一次 fsync"，只是这块 NVMe 快一个量级。
   附带的结果是：**事务内多写一条任务行的边际成本这次测出来了**——+1.8～2.1 ms / 吞吐 −18%～−22%（两次运行同向同量级，
   §7），旧机器上则落在噪声里测不出。
10. **崩溃恢复 2.05–3.68 s（5 次采样）**：几乎全部是"剩余租约 2 s"加上"接手方轮询退避到上限 2 s"。
    本文同时**修正了旧文档的一处推导错误**：那里的"可解释上界 2.53 s"是按轮询下限 250 ms 算的，
    漏掉了退避到 `MaxPollInterval`=2 s 的那一档，现在改为 4.29 s（§9）。

**这份文档不能用来声称**：比 RabbitMQ/Redis 快、能支撑每秒多少任务、某个具体延迟上限。
它甚至不能用来声称"这台机器上 GoRangeTask 的天花板是 1000 task/s"——W=32 时连接池（32）已经顶满，
再往上要先改池，本次没测（§11）。

## 1. 怎么跑

```bash
# 一条命令跑完整矩阵（会先检查容器是否在跑）
scripts/bench.sh

# 单独跑某个场景
export GOTASK_BENCH_DSN='root:rootpw@tcp(127.0.0.1:3306)/gotask_bench?parseTime=true&loc=UTC&timeout=5s&readTimeout=30s&writeTimeout=30s'
go run ./bench -scenario drain -workers 1,4,16 -sizes 256,4096,32768 -tasks 1000
go run ./bench -scenario latency -workers 1,4 -arrivals 100ms,500ms
go run ./bench -scenario txcheck -txcount 10000
go run ./bench -scenario recovery
```

本文的数字用下面这条**等价命令**跑出来（参数与 `scripts/bench.sh` 逐项相同）：

```bash
go build -o bench/bench.exe ./bench
GOTASK_BENCH_DSN='root:rootpw@tcp(127.0.0.1:3306)/gotask_bench?...' \
  ./bench/bench.exe -scenario all -tasks 1000 -workers 1,4,16 -sizes 256,4096,32768 \
  -producers 8 -enqueues 800 -idle 20s -timeout 5m -container gotask-mysql \
  -out bench/results/$(date +%Y%m%dT%H%M%S)-baseline.json
```

**为什么不用 `go run`**：这台机器上（Windows + 本仓库的采集沙箱）`go run` 在
`fork/exec ...\Temp\go-build*\exe\bench.exe` 处被拒绝（Access is denied），
所以改成"先 `go build` 到一个持久路径、再直接执行"。两种方式的程序与参数完全一致，
区别只在二进制放在哪；`scripts/bench.sh` 本身仍用 `go run`，在普通终端里可用。

几个测量约定沿用旧文档：原始样本不折叠（分位数用最近秩法从原始样本取，不插值）、
分位数不相减（"入队开销"只比均值与吞吐）、计数必须自洽（drain 结束核对"指标说完成 N 条 =
库里 N 条 `succeeded`"，对不上以非零码退出）、等待排空看指标计数而不是轮询 `COUNT`。

**Windows 上的环境采集**：`bench/` 原先把机器信息写死在 `/proc` 里，在 Windows 上会得到
`CPU=unknown / 内存=0 / load=unknown`。本次补了 `bench/sysinfo_windows.go`（build tag）：
CPU 型号读注册表、内存问 `GlobalMemoryStatusEx`、负载改用"1 s 采样的 CPU 利用率"
单列 `cpu_util_before/after` 字段——**Windows 没有 load average，不拿利用率冒充它**。
所以本文 JSON 里 `load_avg_*` 是 `"n/a"`，看 `cpu_util_*`。

| `innodb_buffer_pool_size` | 128 MB |
| `innodb_flush_log_at_trx_commit` | 1（每次提交都 fsync） |
| `sync_binlog` | 1（binlog 也每次 fsync） |
| `transaction_isolation` | READ-COMMITTED |
| `innodb_flush_method` | fsync（容器默认，未改） |
| 网络 | 端口转发到 `127.0.0.1:3306`，**不是纯内核 loopback**：Windows → WSL2 VM 多一跳 |
| 连接池 | MaxOpenConns=32 / MaxIdleConns=32 / ConnMaxLifetime=0 |
| Worker | PollInterval 250 ms、MaxPollInterval 2 s、BatchSize 1、LeaseDuration 30 s、HeartbeatInterval 10 s、**回收器与清理器均关闭** |

三点必须写在数字前面：

- **MySQL 跑在 WSL2 的虚拟盘（VHDX）上**。一次 fsync 要穿过 `ntfs → VHDX → ext4` 两层，
  与旧机器的原生 ext4 不是同一条路径。这影响两件事：每次提交的**延迟**，以及并发下的**吞吐上限**
  （VHDX 的 I/O 提交更像"单队列"）。所以 §13 的跨机器对照只能读量级与形状，不能读倍数。
- **宿主不是空闲机器**：`vmmemwsl` + WorkBuddy + 杀毒软件常年占 15–25% 的 CPU（16 线程合计）。
  这与旧文档"同机还有别的进程"是同一类问题，只是程度轻一些。
- **回收器与清理器关闭**是为了把"干净的吞吐"与"后台维护的代价"分开测。默认部署下它们开着
  （30 s / 1 h 一次），**它们的代价不包含在本文任何数字里**（§11）。

## 3. 入队延迟

三种模式，8 个并发 producer，每种 800 次调用：

- `producer_tx_baseline`：只在一个事务里插业务行（`bench_orders`），不碰任务表——"没有队列"的基线。
- `producer_tx`：同一个事务里插业务行 + `EnqueueTx`——本库推荐用法。
- `enqueue`：单独调 `Enqueue`（自动提交），没有业务事务。

| 模式 | 运行 | 吞吐 (次/s) | p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|
| `producer_tx_baseline` | 1 | 991.3 | 7.58 ms | 10.72 ms | 13.78 ms | 19.24 ms |
| （同上） | 2 | 970.2 | 7.93 ms | 10.77 ms | 12.22 ms | 13.28 ms |
| `producer_tx` | 1 | 772.0 | 9.64 ms | 13.91 ms | 15.95 ms | 20.96 ms |
| （同上） | 2 | 796.2 | 9.67 ms | 13.11 ms | 16.09 ms | 19.70 ms |
| `enqueue` | 1 | 1128.4 | 6.41 ms | 9.14 ms | 15.61 ms | 45.45 ms |
| （同上） | 2 | 1225.2 | 5.96 ms | 9.44 ms | 11.85 ms | 16.63 ms |

**怎么读**：一次提交要 fsync 两次（redo + binlog），8 个 producer 的提交被 group commit 合在一起落盘，
所以 p50 是"等一次落盘"而不是"等八次"。**这不是 GoRangeTask 的开销**：不碰任务表的
`producer_tx_baseline` 也是同一个量级。`enqueue` 更快（p50 6.0–6.4 ms）是因为它只有一次自动提交、
且没有业务行要写；它的 max（45 ms，出现在第 1 次运行）是一次偶发的落盘抖动，不是稳定特征。

## 4. 吞吐与伸缩

每个场景预置 1000 条任务（一个事务批量入队，避免把 1000 次 fsync 算进"预置耗时"），然后让 Worker 排空。
表为第 1 次运行；第 2 次见 §10。

| 并发 | payload | 吞吐 (task/s) | 排空 (s) | claim p50/p95/p99 | 排队 p95 | 处理 p95 |
|---|---|---|---|---|---|---|
| 1 | 256 B | 66.2 | 15.10 | 10.0 / 11.7 / 12.9 ms | 14449 ms | 0.00 ms |
| 4 | 256 B | 251.2 | 3.98 | 9.9 / 12.8 / 14.2 ms | 3858 ms | 0.00 ms |
| 16 | 256 B | 675.5 | 1.48 | 14.5 / 17.9 / 20.9 ms | 1727 ms | 0.00 ms |
| 1 | 4096 B | 62.2 | 16.08 | 10.5 / 12.3 / 13.8 ms | 15381 ms | 0.00 ms |
| 4 | 4096 B | 217.3 | 4.60 | 11.2 / 14.0 / 15.4 ms | 4410 ms | 0.00 ms |
| 16 | 4096 B | 617.2 | 1.62 | 15.7 / 20.4 / 21.6 ms | 1748 ms | 0.00 ms |
| 1 | 32768 B | 60.1 | 16.64 | 10.9 / 13.6 / 15.9 ms | 15977 ms | 0.00 ms |
| 4 | 32768 B | 234.7 | 4.26 | 10.6 / 13.3 / 15.5 ms | 4181 ms | 0.00 ms |
| 16 | 32768 B | 588.1 | 1.70 | 17.2 / 21.3 / 24.7 ms | 2372 ms | 0.00 ms |

**怎么读**：

- **W=1→4 是 3.5–3.9 倍，接近线性**：领取是 `FOR UPDATE SKIP LOCKED`，四个消费者互不阻塞；
  同时 group commit 把 4 次提交合成一次落盘，所以吞吐不是"4 倍"，而是"4 倍并发 × 摊薄 fsync"。
- **W=4→16 是 2.4–2.9 倍**（256 B：251 → 676，即 2.7 倍）：4 倍的 Worker 换来 2.7 倍的吞吐，
  每 worker 从 63 降到 43 task/s。claim p50 从 10 ms 涨到 14.5–17.2 ms，但**没有旧机器那种数量级恶化**
  （那边是 25 → 125 ms，§13）。
- **payload 影响很小**：256 B 与 32 KB 在 W=1 时只差 10%（66.2 vs 60.1），说明成本在"提交次数"
  而不是"行大小"。32 KB 在 W=16 时掉到 588（vs 675），是 16 个 32 KB 行同时触发 redo/页分裂带来的额外 I/O。
- **"排队 p95" 在这张表里是积压的度量，不是调度的度量**：1000 条任务排队，最后一个自然要等整队排空。
  要看调度开销请看 §6.2。

### 4.1 补充探针：W=32 还在涨，但池子顶满了

固定矩阵停在 16 是因为旧机器只有 4 核、16 已超配。这台机器 16 线程、MySQL 也没吃满，
所以补跑了一组（**单独存证、不进主矩阵**，任务数 2000 以提高稳定性）：

| 并发 | payload | 任务数 | 吞吐 (task/s) | claim p50/p95 | 池最高占用 | 锁等待 | MySQL CPU 均值/峰值 |
|---|---|---|---|---|---|---|---|
| 32 | 256 B | 2000 | 999.8 | 20.3 / 26.2 ms | 32（= 上限） | 1 次 / 2 ms | 183% / 366% |
| 32 | 32768 B | 2000 | 781.2 | 25.7 / 33.2 ms | 32（= 上限） | 3 次 / 2 ms | 216% / 343% |

W=16→32 只多 1.4–1.5 倍，且**连接池已经顶到 32**：再往上加 Worker 只会排队等连接。
所以"这台机器能到多少 task/s"这个问题**本次没有答案**——要回答它，得先把池调大、
再确认 WSL2 的虚拟盘能不能承受 32+ 条并发提交。这属于后续工作（§11）。

## 5. 资源占用与 DB 成本

| 并发 | payload | 锁等待 次/ms | DB 语句数 | 池最高占用 | MySQL CPU 均值/峰值 |
|---|---|---|---|---|---|
| 1 | 256 B | 0 / 0 | 6004 | 1 | 31% / 35% |
| 4 | 256 B | 0 / 0 | 6013 | 4 | 54% / 82% |
| 16 | 256 B | 0 / 0 | 6049 | 16 | 94% / 187% |
| 1 | 4096 B | 0 / 0 | 6004 | 1 | 34% / 35% |
| 4 | 4096 B | 0 / 0 | 6013 | 4 | 61% / 77% |
| 16 | 4096 B | 0 / 0 | 6049 | 16 | 91% / 181% |
| 1 | 32768 B | 0 / 0 | 6004 | 1 | 34% / 39% |
| 4 | 32768 B | 0 / 0 | 6013 | 4 | 64% / 96% |
| 16 | 32768 B | **1 / 0** | 6049 | 16 | 115% / 227% |

（CPU 单位是"单核百分比"，可以超过 100%；`samples` 见 JSON。第 2 次运行同形，锁等待只有 W=16/32 KB 那一格 1 次。）

**三个可验证的结论**：

1. **每个任务恰好 6 条 SQL，且与并发无关**：6004（W=1）/ 6013（W=4）/ 6049（W=16）对应 1000 条任务，
   差值 0.8% 以内；W=32 的 2000 条任务对应 12097 条（6.05/任务）。这 6 条是：claim 事务的
   `BEGIN + SELECT ... FOR UPDATE SKIP LOCKED + UPDATE ... running + COMMIT`，提交后按主键回读整行的 `SELECT`，
   以及写回终态的 `UPDATE`。**并发升高不产生额外语句**，意味着没有死锁重试、没有重复领取。
2. **连接池占用正好等于 Worker 数**（1 / 4 / 16，上限 32），`wait_count` 全为 0 直到 W=32 才顶满：
   池没有成为瓶颈，也没有连接泄漏。
3. **MySQL CPU 始终低于 2.2 个核**：W=16 时 0.9–1.4 个核，W=32 时 1.8–2.2 个核。
   **这台机器上 MySQL 不是瓶颈**——旧机器在 W=16 就打到 1.4–1.9 个核（而它只有 4 个逻辑核），
   两者结论相反，原因在机器不在代码（§13）。

**为什么 W=1 恰好是 66 task/s**：每条任务两次持久提交 × 一次 fsync 约 7.5 ms ≈ 15.1 ms，
而 Handler 是空操作（处理 p95 = 0.00 ms）。两次运行的这个格子是 15.10014 s 与 15.10047 s，
差 0.3 ms —— 它由磁盘时钟决定，调度抖动挤不进去。这也解释了为什么加并发收益大：
并发让多次提交共享同一次落盘（group commit），而不是让单次提交变快。

## 6. 空队列轮询与稳态排队延迟

### 6.1 空队列轮询的成本

空队列时 Worker 按 250 ms 起步、指数退避到 2 s（equal jitter，实际间隔 [上限/2, 上限]）。跑满 15 秒观测窗口：

| 并发 | 观测窗口 | DB 语句数 | DB QPS | 每 worker QPS | MySQL CPU 均值 |
|---|---|---|---|---|---|
| 1 | 15.0 s | 29 | 1.93 | 1.93 | 1.4% |
| 4 | 15.0 s | 122 | 8.13 | 2.03 | 1.4% |
| 16 | 15.0 s | 467 | 31.12 | 1.95 | 2.8% |

**不要把这个 QPS 读成"任务/s"**：一次空轮询是 `BEGIN + SELECT + COMMIT` 三条语句，
所以 1.93 QPS ≈ 0.64 次轮询/s，与"退避到 2 s 上限"同量级。
**每 worker 约 2 QPS 且与并发数成正比**：100 个空闲 Worker ≈ 200 QPS、MySQL CPU 个位数百分比。
第 2 次运行是 1.93 / 7.73 / 31.93，与第 1 次相差 <5%——这是全文最"硬"的一个数，因为它只由配置决定。

### 6.2 稳态排队延迟

方法是"让队列永远不积压"：按固定间隔（100 ms / 500 ms）一条一条入队，Worker 必须跟得上，
于是测到的是**从入队到 Handler 开始**的等待，而不是"前面还有多少条"。

| 并发 | 入队间隔 | 任务数 | 排队 p50 | 排队 p95 | 排队 p99 | 排队 max | claim p95 |
|---|---|---|---|---|---|---|---|
| 1 | 100 ms | 200 | 103.6 ms | 209.4 ms | 237.9 ms | 252.9 ms | 12.0 ms |
| 4 | 100 ms | 200 | 56.8 ms | 139.1 ms | 195.6 ms | 250.2 ms | 11.5 ms |
| 1 | 500 ms | 60 | 214.9 ms | 413.8 ms | 949.2 ms | 949.2 ms | 11.3 ms |
| 4 | 500 ms | 60 | 137.3 ms | 383.1 ms | 411.0 ms | 411.0 ms | 11.4 ms |

**怎么读**：Handler 什么都不做（处理 p95 = 0.00 ms），等待**全部来自"多久看一次队列"**。

- 到达间隔 100 ms 时 p50 是 103.6 / 56.8 ms，约为轮询间隔的一半到四分之一——符合"均匀到达、平均等半个轮询周期"。
- 到达间隔 500 ms 时 p50 升到 214.9 / 137.3 ms、p99 到 949 / 411 ms：队列在两次领取之间常常是空的，
  Worker 已经退避（500 ms → 1 s → 2 s），下一条任务要等下一次轮询才被发现。**延迟变大的原因不是负载，而是稀疏。**
- 加 Worker 能把 p50 降 45%（100 ms 间隔）与 36%（500 ms 间隔），但降不到"除以 4"：
  它不是"处理不过来"，所以加消费者只能提高"撞上正确时机"的概率。
  要真正压低它只能调小 `PollInterval`，代价是空转轮询变密（这一组对照仍未测，§11）。
- 这是全文唯一比旧机器**略好但不显著**的指标（旧机器 p95 260–500 ms，本机 139–414 ms），
  因为它由配置而不是机器决定——快机器只能把手抖部分去掉。

## 7. 入队对调用方事务的边际成本

同一事务形状下，多写一条任务行的代价（`producer_tx` 对比 `producer_tx_baseline`，8 个 producer）：

| 运行 | baseline 均值 | 含任务行均值 | 差值 | 吞吐 baseline → 含任务行 | 变化 |
|---|---|---|---|---|---|
| 1 | 7.89 ms | 10.01 ms | **+2.12 ms** | 991.3 → 772.0 次/s | −22.1% |
| 2 | 8.07 ms | 9.90 ms | **+1.82 ms** | 970.2 → 796.2 次/s | −17.9% |

**这次两次运行给出的是同一个答案**（+1.8 / +2.1 ms，−18% / −22%），方向、量级都一致。
旧机器上同一实验给出 +3.3 ms 与 +30.5 ms 两个互不相容的估计，只能判"测不出"；这里可以判"测得出"。

**能说的**：在这台机器、8 个并发写入者、每次提交都要落盘的配置下，事务里多写一条任务行让
**每笔事务的平均延迟多约 2 ms、吞吐少约两成**。这 2 ms 不是纯 CPU 成本——更大的可能是
8 个 producer 同时往任务表的同一段索引插行，页闩锁与索引维护带来的排队（§5 的锁等待是 0，
因为那是行锁计数，不含页闩锁）。

**不能说的**：这不等于"GoRangeTask 拖慢了业务 20%"。对照组只是"少写一张表"，
它衡量的是一条 INSERT 加上一个二级索引的代价，任何直接写 SQL 的方案都要付。要把它归因到
"本库的实现方式"，还需要一组"手写同样的 INSERT 但不用本库"的对照——没做。

## 8. 事务完整率

口径（需求 §10.3 要求的是"提交时两者同时存在、回滚时两者同时不存在"，这里把它量化；公式见《STAR》）：
已提交业务记录中存在对应任务的记录数 ÷ 已提交业务记录总数。

| 项 | 值 |
|---|---|
| 事务总数 | 10,000（5,000 提交 / 5,000 回滚，严格对半） |
| 并发调用方 | 8 |
| 耗时 | 11.7 s（约 856 笔/s） |
| 已提交业务行 | 5,000 |
| 其中**有对应任务** | 5,000 |
| **事务完整率** | **100.00%** |
| 回滚后残留业务行 | 0 |
| 孤儿任务（有任务行、没有业务行） | 0 |

**为什么这样核对**：只报一个"100%"不够，必须同时看到两个 0——否则"回滚后残留业务行"与
"入队成功但业务回滚"这两类错误可以互相掩盖成一个漂亮的比例。业务行与任务行靠**幂等键携带业务行主键**
（`txcheck-<order_id>`）逐行对上，比的是对应关系，不是两侧总数相等。

**这个 100% 说明什么、不说明什么**：它证明"业务行与任务行在同一事务里要么都提交要么都不存在"，
也就是本库的卖点成立；它**不**证明 GoRangeTask 比直接在业务代码里写 SQL 更快或更可靠。
11.7 s 这个速度只说明这块盘的 fsync 比旧机器快（旧机器同规模 67.3 s），**不是**一个可以外推的容量数字。

## 9. 崩溃恢复耗时

要回答的问题是"Worker 在持有任务时消失，多久之后任务会被别人接手跑完"。这个时间由三部分构成，
而且**可配置**：剩余租约 + 一个回收周期 + **最多一次退避到上限的轮询**（外加领取与执行）。

配置：租约 2 s / 心跳 666 ms / 回收周期 250 ms / 停机预算 500 ms；接手方 B 的轮询 250 ms 起、
上限 2 s（equal jitter）。**连测 5 次**（旧文档只有 1 次）：

| 次 | 剩余租约 | 恢复耗时 | 最终状态 | 两个 Handler 执行次数 | 陈旧写回 |
|---|---|---|---|---|---|
| 1 | 1993 ms | **3.68 s** | `succeeded`，`attempt=2` | A=1 / B=1 | 被拒（`ErrLeaseLost`） |
| 2 | 1992 ms | **2.05 s** | 同上 | A=1 / B=1 | 被拒 |
| 3 | 1993 ms | **3.44 s** | 同上 | A=1 / B=1 | 被拒 |
| 4 | 1993 ms | **3.33 s** | 同上 | A=1 / B=1 | 被拒 |
| 5 | 1994 ms | **2.53 s** | 同上 | A=1 / B=1 | 被拒 |

**中位数 3.33 s，范围 2.05–3.68 s，上界 4.29 s**（= 1.99 剩余租约 + 0.25 回收周期 + 2.0 最大轮询 + 0.05 领取执行）。

**为什么不是固定的 2 秒多一点**：租约到期那一刻，接手方 B 正在空轮询（任务还是 `running`，它什么都领不到），
退避已经按 250 → 500 → 1000 → 2000 ms 爬上去。B 下一次"能看见"任务的时刻 = 租约到期 + 它在当前档位剩余的睡眠。
所以恢复耗时是一个**由退避抖动决定的分布**：运气好落在 2.05 s（刚睡醒），运气差落在 3.68 s（睡在最长的 2 s 档）。

**这次同时修正了旧文档的一处推导错误**：旧版把上界写成"剩余租约 + 回收周期 + **一次轮询 250 ms** + 执行"= 2.53 s。
那个公式用错了轮询间隔——B 空转时用的是**退避后的**间隔，上限是 `MaxPollInterval` 2 s，不是 `PollInterval` 250 ms。
旧机器上实测 2.07 s 恰好没越界，所以错误没暴露；这台机器第一次测到 3.63 s 就把它顶穿了。
`bench/scenarios.go` 已改为按 `recoveryPollMax` 推导，并把 B 的轮询参数提成常量，避免配置与公式漂移。

**这个修正改变了什么结论**：
- "恢复耗时 ≈ 剩余租约 + 最多一个回收周期 + 最多一次轮询"这个**机制**没变，变的是"一次轮询"的量级（2 s，不是 0.25 s）。
- 因此**恢复时间的主要旋钮不只是 `LeaseDuration`，还有 `MaxPollInterval`**：把退避上限压到 200 ms，
  5 次采样会全部收在 2.3 s 附近；代价是空队列轮询变密（§6.1 的 100-worker 估算会翻十倍）。
- 旧文档"2.07 s 已接近该配置下的上界"这句话**不再成立**——按修正后的上界，2.07 s 只是分布的左端。

**为什么不用真的 `kill -9`**：进程消失对数据库留下的痕迹只有两件事——租约不再被延长、也没有人写回。
让一个 Handler 无视 ctx 卡住、再取消 Worker 的 `Run`，产品语义恰好产生同样的库侧状态
（`Run` 在 `ShutdownTimeout` 后放弃等待并返回 `ErrShutdownTimeout`，续租看护随停机一起停掉），
而且完全确定、可重复。代价是那个 Handler 的 goroutine 还活着，所以测量结束时会放行它，
并断言它拿着陈旧 epoch 的写回被拒绝——这一条同时是 fencing 的端到端证据。

**"旧 worker 复苏"的完整故障注入**（真子进程 + `SIGSTOP` + 接管 + 解冻 + 整行快照零改动）在
`store/mysql/revival_integration_test.go`，那里验证的是"写回被拒且一个字段都没变"，不是耗时。
注意：该测试用 `syscall.SIGSTOP`，**只在 Unix 上编译**，Windows 上 `go test ./...` 会在这个文件上失败（§11）。

## 10. 重复性

同一个矩阵连跑两次（宿主 CPU 利用率 32%→20% 与 19%→15%），单位 task/s：

| 场景 | 第 1 次 | 第 2 次 | 极差 |
|---|---|---|---|
| W1 / 256 B | 66.2 | 66.2 | 0.0% |
| W4 / 256 B | 251.2 | 260.4 | 3.5% |
| W16 / 256 B | 675.5 | 714.0 | 5.4% |
| W1 / 4096 B | 62.2 | 64.4 | 3.5% |
| W4 / 4096 B | 217.3 | 245.1 | 11.3% |
| W16 / 4096 B | 617.2 | 714.0 | 13.6% |
| W1 / 32768 B | 60.1 | 62.0 | 3.0% |
| W4 / 32768 B | 234.7 | 219.3 | 7.0% |
| W16 / 32768 B | 588.1 | 520.7 | 12.9% |

**四条观察**：

1. **W=1 完全可复现**（66.2 与 66.2，排空 15.10014 s vs 15.10047 s）：它由"每任务 2 次 fsync"决定，与调度无关。
2. **并发越高，波动越大**（W=16 最差 13.6%），因为此时吞吐取决于 group commit 的合批情况与页闩锁排队，
   两者都对宿主的调度抖动敏感。旧机器同一格能差 45%，这里不到三分之一——**机器更干净，结论才更稳**。
3. **空队列 QPS 几乎完全可复现**（1.93 / 1.93、8.13 / 7.73、31.12 / 31.93）：由配置决定，与负载无关。
4. **入队延迟的重复性也变好了**（baseline 991 / 970 次/s，p50 7.58 / 7.93 ms）：旧机器是 105.8 / 202.5 次/s。

**但"重复性好"不等于"可以外推"**：这台机器的背景负载仍在 14–32% 之间漂移，且 MySQL 跑在虚拟盘上。
所有吞吐数字仍应读作"这个量级"，不是"这个值"。

## 11. 由此得出的工程结论

- **瓶颈位置随机器改变，代码没有改变**。旧机器上"4 倍 Worker 换 1.4–1.9 倍吞吐、claim 延迟涨 5 倍"
  看起来像库的伸缩性问题；换到这台机器，同一份代码在 W=4→16 拿到 2.7 倍、claim p50 只从 10 ms 涨到 17 ms。
  所以那条结论是**环境结论**（4 逻辑核 + 笔记本盘），不是库的性质。对外讲述时必须带上机器。
- **低并发下的吞吐由"每任务几次 fsync"决定，不由并发控制决定**。W=1 的 66 task/s 就是
  `1 / (2 × 7.5 ms)`。想让低并发更快，只能减少持久提交次数（`BatchSize` 批量化能把 claim 的 fsync 摊到 N 条任务上），
  或者换更快的盘/关掉 `sync_binlog`（后者是可靠性取舍，不是优化）。
- **`BatchSize` 是下一个该测的旋钮**，现在理由比旧文档更硬：它直接作用在"每任务 2 次 fsync"里的第一次上。
  预期是低并发吞吐接近翻倍，代价是单次事务的锁范围与重试粒度变大——需要单独测。
- **`PollInterval` / `MaxPollInterval` 同时是延迟旋钮和恢复旋钮**：§6.2 的排队延迟由它们决定，
  §9 的恢复时间上限也由 `MaxPollInterval` 决定。这组对照（延迟降多少 / 空转涨多少 / 恢复快多少）仍未测。
- **回收器与清理器的代价没有进本基线**：它们默认开着（30 s / 1 h），一次回收是"加锁读 + 分流写回"的短事务，
  一次清理是"加锁读 + 批量删"。要在有积压的真实负载下评估。
- **本次明确留下的四个缺口**：
  1. **吞吐上限没测到**：W=32 时连接池（32）顶满、MySQL 只用 2 个核，再往上要改池，本次没做。
  2. **WSL2/VHDX 的 fsync 是否真的落到物理盘没有验证**。如果它被宿主缓存吸收，§3/§4 的延迟会偏乐观。
     要主张持久性，得单独做"提交后强杀容器/断电"的落盘验证。
  3. **边际成本没有"手写同一条 INSERT"的对照**（§7）。
  4. **Windows 上 `go test ./...` 跑不起来**：`store/mysql/revival_integration_test.go` 用了
     `syscall.SIGSTOP`，没有 build tag。本基线只跑 `bench/`，没有改动测试；要做 Windows 上的全量测试需另开一笔。

## 13. 与 i5-8200Y 那台的对照

同一份代码、同一套 MySQL 参数（8.0.46 / buffer pool 128 MB / flush=1 / sync_binlog=1 / RC）、
同一套 Worker 配置与测法，只有机器不同：

| 指标 | i5-8200Y（4 逻辑核，2026-10-17） | Ryzen 7 8745H（8C16T，本文） |
|---|---|---|
| 256 B，W=1 / 4 / 16 | 24–29 / 47–49 / 66–96 task/s | 66 / 251–260 / 676–714 task/s |
| W=4→16 的倍数 | 1.4–1.9× | 2.4–2.9× |
| claim p50（W=1 → W=16） | 25 → 125 ms | 10 → 14–19 ms |
| MySQL CPU（W=16） | 144% 均值 / 185% 峰值（4 核机器，已饱和） | 91–142% 均值 / 181–227% 峰值（16 线程，远未饱和） |
| 入队 p50（8 producer） | 27–70 ms | 6.0–9.7 ms |
| 事务内多写一条任务行的代价 | 测不出（+3.3 / +30.5 ms 互相矛盾） | **+1.8～2.1 ms，−18%～−22%（两次一致）** |
| 10,000 笔混合事务耗时 | 67.3 s | 11.7 s |
| 崩溃恢复 | 2.07 s（1 次采样，旧上界 2.53 s） | 2.05–3.68 s（5 次，修正后上界 4.29 s） |
| 稳态排队 p95 | 260–500 ms | 139–414 ms |

**怎么读这张表**：

- **能读的是形状**：快机器上 claim 延迟不随并发恶化、W=4→16 接近线性、MySQL CPU 不再是瓶颈；
  慢机器上三者同时恶化。这说明旧机器遇到的"天花板"是 CPU 与磁盘的天花板，与 `SKIP LOCKED` 的算法无关。
- **不能读的是倍数**。两台机器的操作系统（Linux vs Windows）、I/O 路径（原生 ext4 vs WSL2 VHDX）、
  背景负载都不同，7–11 倍这个数字里混着所有因素。它只能说明"同一份代码在不同硬件上的量级差"。
- **排队延迟几乎不受机器影响**（139–414 vs 260–500 ms）：因为它由 `PollInterval` 与退避决定，
  这一点反过来验证了 §6.2 的归因是对的——快机器只去掉了尾部的抖动。
- **恢复耗时的"变慢"不是退化**：5 次采样的中位数 3.33 s 大于旧机器的 2.07 s，原因是接手方轮询退避的
  随机相位，不是库慢了；修正后的上界 4.29 s 覆盖了旧机器那一格（2.07 s 只是运气好）。
