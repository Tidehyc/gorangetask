## 0. 这份文档怎么用

优先级不是按"想要什么"，而是按**"缺的是功能还是证据"**分：

| 级别 | 含义 | 判断依据 |
|---|---|---|
| P0 | 证据缺口：能力已实现，但没有可信的数字或明确的"测不出"结论 | 读性能基线 §11 会看到"未测" |
| P1 | 能力缺口：有能力做，但公开面不完整或语义有洞 | 读 README「已知边界」会看到"仅此而已" |
| P2 | 工程化：不影响正确性，只影响协作与发布可信度 | 发版/CI/文档流程上的摩擦 |

每条都按四要素写：**目的 / 做法 / 验收 / 现有落点**。验收必须是"一条命令或一个文件能复核"的东西——这是本项目一贯的纪律，不是形式。

## 2. P0：补齐证据（不改行为）

### P0-1 批大小的成本与安全边界

- **目的**：`BatchSize` 默认 1，等于"一任务一次 claim 事务"。批量化可能摊薄每任务 6 条 SQL 里的 claim 部分，但会让加锁读一次拿多行——这正是附录 A 那次事故的形状。
- **做法**：给 `bench` 加 `-batch` 旋钮（现在 5 处全硬编码 1：`bench/main.go:744`、`bench/main.go:941`、`bench/scenarios.go:93`、`:451`、`:513`），扫 1 / 4 / 16 / 64。每档记录 task/s、每任务 SQL 数、`Innodb_row_lock_waits`，以及 claim 的 `EXPLAIN`（`key` / `rows` / 是否 `filesort`）。
- **验收**：四档对照表进性能基线；**如果加锁范围随 batch 放大，先修（`FORCE INDEX` 或调整 claim SQL）再报数字**，不许"先出数后补坑"。同时补一条并发加锁用例（参照 `TestReapLockingReadStaysOnLeaseIndex` 的写法：两个手写事务，断言取到的行不相交）。
- **现有落点**：`worker.go:465`（`Limit: w.cfg.BatchSize`）、`config.go:26-31`、`store/mysql/worker.go:303`（`selectClaimableIDs`）。
- **工作量级**：中（改 bench + 一条新用例）。

### P0-2 PollInterval 的成本曲线

- **目的**：稳态排队延迟几乎完全由它决定（250 ms → p50 约 130 ms），但"调到 50 ms 要付多少空转 QPS"没有数据。
- **做法**：`-arrivals` 已能控制入队节奏，扫 `PollInterval` = 50 / 100 / 250 / 500 ms 四档，同时记稳态 p50/p95 与空队列每 worker QPS。
- **验收**：一张四行表 + 一句可被数据支撑的结论（延迟随 `PollInterval` 近似线性；空转 QPS 近似反比）。结论若只在两档之间成立，就只写两档。
- **现有落点**：性能基线 §6.2（[本机](./GoRangeTask-性能基线-Ryzen7-8745H.md) 与[旧机](./GoRangeTask-性能基线.md) 都有该节）。
- **工作量级**：小（bench 已有 latency 场景，加一个参数）。

### P0-3 回收器与清理器的开销

- **目的**：基线**故意关掉了这两个协程**（`bench/main.go:747-748`、`:944-945`，`ReapInterval=-1` / `CleanupInterval=-1`），而生产默认是开着的（30 s / 1 h）。所以现在的吞吐数字是"没有后台职责时的上界"，不是生产形态。
- **做法**：同一负载下开/关对比；另用 `dbCounters` 差值单独测"一轮回收 ≈ 多少条 SQL、多少毫秒"和"一轮清理（默认批 1000）≈ 多少"。
- **验收**：给出"每轮回收 X 条 SQL / Y ms，对稳态吞吐影响 ≤ Z%"——Z 必须是实测值；测不出就写"在噪声内测不出"，并说明噪声有多大。
- **现有落点**：`worker.go:641`（`reapLoop`）、`worker.go:699`（`cleanupLoop`）、`config.go:41/68`。
- **工作量级**：中。

### P0-4 事务入队边际成本：已测出（2026-10-18 换机器后）

- **结论**：旧机（i5-8200Y，4 逻辑核）两轮给出 **+3.3 ms** 与 **+30.5 ms** 两个互不相容的估计，当时判定"本机不可测，不采信单次数据"。2026-10-18 在 Ryzen 7 8745H 上按同一跑法重测：**+1.8～2.1 ms、吞吐 −18%～−22%，两轮同向同量级** ⇒ 测得出来。**旧结论不是库的性质，是那台 4 核机 fsync 抖动的性质**，两套结论都保留在文档里。
- **仍未做**：缺一个"手写同一条 `INSERT`"的对照，所以现在只能说"事务内多写一条任务行要付多少"，还不能把它拆成"库的开销"与"fsync 的开销"。
- **验收**：补上对照后写进两份性能基线的 §7；在那之前对外只引用区间与"两轮一致"，**不引用单轮数字**。
- **现有落点**：[本机基线](./GoRangeTask-性能基线-Ryzen7-8745H.md) §7、[旧基线](./GoRangeTask-性能基线.md) §7。
- **工作量级**：小（补一个对照写法）；原"大（换环境）"这一步已完成。

### P0-5 覆盖率与用例计数复测

- **目的**：进度跟踪 §6「Race 检查」那行的 100.0% / 91.4% 是 **2026-10-15** 的数字，此后新增了 601 行集成测试和 20 多个用例，数字没有复测。
- **做法**：`go test -coverprofile` 跑三个有测试的包，重算百分比并写日期。
- **验收**：更新 §6 两个数字并带日期；顺带对比多次运行的非零分支差集——**覆盖率在两个值之间浮动就是诊断信号**，说明有分支只是偶尔被执行。
- **现有落点**：`docs/GoRangeTask-进度跟踪.md` §6 Race 行。
- **工作量级**：小（最便宜的一项，建议先做）。

## 3. P1：能力增强

### P1-1 积压查询 API

- **目的**：公开面只有"按 ID 查任务"，运维要看积压得自己写 SQL（`SELECT queue_name, status, COUNT(*) ... GROUP BY`）。宿主自己写容易绕开库对索引的约定，写出全表扫描。
- **做法**：`Client.Stats(ctx) ([]QueueStat, error)`，按 `(queue, status)` 聚合，只允许固定 status 集合、带 `LIMIT` 上限；或 `Client.List(ctx, Filter)` 做只读分页。
- **验收**：`EXPLAIN` 走 `ix_gotask_claim` / `ix_gotask_cleanup`，无 `filesort`；空表返回空切片而不是 nil。
- **边界**：只读聚合，不做"修改任务状态"的管理 API——那会把库变成半个后台系统。

### P1-2 幂等键的保留策略

- **目的**：清理是物理删除，任务行没了幂等键就释放（README「已知边界」）。要"永不重复"就得把键单独留住。
- **做法**：先写 ADR 定语义（保留下限多久、谁来清、与任务行的关系），再动 schema。新表必须能 `ALGORITHM=INSTANT` 创建/加列（参考 `go-mysql-schema-migration-safety` 的约束）。
- **验收**：**两条用例都要有**——删除任务行后同键再入队被拒；保留期过后允许复用。只做前者等于把边界换了个位置，语义反而更含糊。

### P1-3 Prometheus 指标适配器

- **目的**：`Metrics` 是具名事件接口，每个宿主都要自己写一遍适配；README 提到 Prometheus，但仓库里没有实现。
- **做法**：可选子包 `adapter/prometheus`，把 `observability.go` 的 12 个具名事件映射成 Counter/Histogram。
- **验收**：`testutil` 抓取用例，断言指标名与标签集合稳定；`go mod graph` 证明核心包不依赖 prometheus 客户端（依赖只能进 adapter）。
- **风险**：**标签基数**。`queue` / `type` 是外部可控输入，文档必须写明基数上限建议，否则一个打错 type 的调用就能炸掉监控。

### P1-4 一次性回收/清理命令

- **目的**：回收与清理只在 Worker 进程内跑；Worker 全下线期间，过期租约只能一直停在 `running`。
- **做法**：`cmd/gorangetask-reap`，复用 `store/mysql` 的 `ReapExpiredLeases` / `CleanupFinished`，必须带 `-dry-run` 先报将影响的行数。
- **验收**：dry-run 与真实执行的行数一致；与运行中的 Worker 并发执行无副作用（§4 已有并发回收用例可复用）。
- **注意**：这是"多给一个入口"，不改回收语义。

### P1-5 多队列优先级

- **目的**：`Queue` 现在只是标签，claim 的排序里没有优先级，高优任务只能靠 `RunAt` 排队。
- **做法**：先定语义（全局优先级 vs 每队列 FIFO），再决定加 `priority` 列还是改 claim 的 `ORDER BY`。
- **验收**：换索引后 `EXPLAIN` 仍走索引、无 `filesort`；`LIMIT` 仍限制加锁范围（并发用例必须补）；老数据的优先级默认值语义写清（NULL vs 0，别留两种含义）。

## 5. 明确不做（写下来是为了别再讨论）

- **Postgres / SQLite 后端**：需求写死 MySQL 8.0+/InnoDB；换库要重做加锁读与索引假设，不是加个方言层的事。
- **跨服务 Broker 语义**（广播、路由、多订阅者）：README 已划界，需要这些请用 Outbox + RabbitMQ。
- **exactly-once 外部副作用**：做不到。库能做的是"至少一次尝试 + fencing 保护任务状态"，副作用幂等必须由 Handler 负责。
- **内置 Web UI / 管理后台**：会引入鉴权、审计、分页等一整套需求，与本库定位冲突。

## 7. 每项的共同验收纪律

做完任何一项，都按这四条自检，缺一条就不算完成：

1. **数字带日期与环境**：没写"在哪台机器、什么 MySQL 参数、哪天"的数字等于没有。
2. **测不出就说测不出**：给出噪声幅度与复现命令，不挑好看的数。
3. **新断言要能失败**：临时破坏实现，确认用例真的红，还原后逐字节一致（`diff` 或 md5）。
4. **对外表述不越界**：能力没发布就说"已提交"，CI 没跑完就说"运行中"，单次运行不写成承诺。
