# GoRangeTask 项目构想：STAR 说明

> 项目名：GoRangeTask（仓库名：`gorangetask`）。
> 文档定位：项目背景与简历叙述，不是实现规格。
> 状态：立项讨论稿 v0.7。项目尚未实现；行动为计划，结果为待验证目标。
> 需求、接口、数据模型和验收细节见《GoRangeTask-需求文档.md》及《GoRangeTask-技术设计.md》。

## S｜Situation：问题从哪里来

Go 后端服务常有一些不需要广播给其他服务、而由本服务后台完成的工作，例如生成报表、处理上传文件、刷新索引或执行延迟补偿。若业务数据提交后，再单独把任务投递给队列，进程可能在两步之间退出，导致数据已提交但任务没有创建；反过来，若先投递任务再提交业务数据，任务也可能先于业务数据生效。

对这种同库、本地后台工作，**把业务数据和任务记录放在同一个数据库事务里写入**，可以保证两者一起提交或一起回滚。直接执行 SQL 完全可以实现这一点，GoRangeTask 不会提供比数据库事务更强的原子性保证。

困难在事务入队之后：多个 Worker 如何避免同时领取同一任务；Worker 崩溃后如何恢复；运行时间超过租约的旧 Worker 如何避免覆盖新状态；失败任务如何退避重试、何时进入死信；Handler 发生重复调用时如何处理幂等。这些机制也能用 SQL 自行实现，但每个服务都需要设计、维护和验证。GoRangeTask 的项目目标是把这套任务执行生命周期封装成可复用的 Go 库。

Outbox + RabbitMQ 解决的是另一类需求：在业务事务中记录待发布事件，再由投递器发给 RabbitMQ，让 Broker 负责路由、缓冲、广播和独立消费者。GoRangeTask 面向同库、本地 Handler 的任务执行，不替代这类事件分发。两者都可以在数据库事务中保存待处理意图，但任务的后续处理路径和职责不同。

### 项目定位

GoRangeTask 是基于 MySQL 的可嵌入 Go 任务队列。它提供事务入队 API 和 Worker 运行时：调用方负责把业务变更和任务行放入同一事务；GoRangeTask 负责领取、租约、续期、恢复、重试和终态记录。它的价值是减少各业务重复实现队列执行机制的工作，并通过一致的语义和测试降低遗漏并发与故障边界的风险。

这不是“用了 GoRangeTask 才能事务写入任务”，也不意味着 GoRangeTask 一定比手写 SQL 或 RabbitMQ 更快。若一个简单任务只需一条 SQL 和一个一次性 Worker，直接实现可能更合适；若任务需要可靠的并发执行、恢复和重试，并希望这些能力可复用，才值得使用或实现这类库。

### 术语解释

- **STAR**：Situation（情境）、Task（任务）、Action（行动）、Result（结果）的项目经历组织方式。
- **MVP**：Minimum Viable Product，最小可验证版本，只实现检验核心设计所需的功能。
- **Producer**：创建任务的业务代码。
- **Worker**：后台进程，从 GoRangeTask 数据库队列领取任务。
- **Handler**：Worker 调用的任务处理函数。
- **租约（lease）**：Worker 在限定时间内持有任务执行权的记录；租约过期后任务可被恢复。
- **Fencing token**：随每次领取递增的租约代次；旧 Worker 写回时若代次已过期，数据库条件更新会拒绝它。
- **幂等**：同一任务重复处理，最终业务效果仍与处理一次相同。
- **至少一次尝试**：已提交任务在 Worker 可用、数据库可用且重试策略允许时会被至少交给 Handler 尝试一次；Handler 可能重复调用，也可能因永久错误或达到次数上限进入死信。

## T｜Task：GoRangeTask 要解决什么

设计并实现一个可复用的 MySQL 任务队列库，提供两段协作但边界清楚的能力：

1. **事务入队 API**：允许调用方在现有数据库事务中插入任务记录。它复用数据库事务能力，不自行创造额外的原子性。
2. **可靠的任务执行生命周期**：让多个 Worker 并发领取任务，并通过租约、恢复、重试、fencing 和死信管理处理执行过程中的并发与故障。

GoRangeTask 对外承诺的是**任务记录持久化，以及按策略至少一次尝试执行**，而不是 Handler 必定成功或外部副作用恰好发生一次。超过最大尝试次数或被标记为永久失败的任务会进入死信；调用方应为可能重复执行的 Handler 实现幂等。

| 维度 | 手写 SQL + 自建 Worker | GoRangeTask | Outbox + RabbitMQ |
|---|---|---|---|
| 事务内原子写入 | 业务数据 + 任务行 | 业务数据 + 任务行，通过 `EnqueueTx` | 业务数据 + Outbox 事件 |
| 后续处理 | 应用自行实现领取、恢复、重试等 | 库的 Worker 运行时调用本地 Handler | Outbox 投递至 RabbitMQ，再由消费者处理 |
| 主要职责 | 取决于应用自建实现 | 本地任务生命周期管理 | 可靠事件交接、路由、广播和消费者解耦 |
| 适用情况 | 任务简单，能接受自建和维护逻辑 | 任务执行需要可复用的并发控制、租约、恢复和重试 | 需要跨服务/语言传递、多个订阅者、Broker 缓冲或路由 |

因此，GoRangeTask 的亮点不是“比 SQL 多保证了一次事务”，而是把任务表背后的领取和执行生命周期做成有明确语义、可测试、可复用的组件。数据库仍是持久化基础，MySQL 负载也需要实测。

## A｜Action：计划如何实现

当前是实现计划，不代表已经完成。

1. 定义稳定的任务模型和 API：普通入队、调用方事务内入队、任务查询与 pending 任务取消；核心包不绑定 ORM，另提供可选 GORM adapter。
2. 使用 MySQL 8.0+ / InnoDB 实现任务表、领取索引和数据库时间判断；在短事务中用 `FOR UPDATE SKIP LOCKED` 并发领取，提交后再运行 Handler。
3. 实现租约续期与过期恢复；为每次领取递增 fencing token，使过期 Worker 不能续租或覆盖当前任务状态；发现租约丢失时取消 Handler context。
4. 实现可配置的最大尝试次数、指数退避、永久失败、死信、终态清理、结构化日志和低基数指标；明确重复执行要求由 Handler 幂等处理。
5. 提供独立示例服务，演示业务行与任务行同事务提交/回滚，以及 Worker 停止、租约回收、重启恢复的过程。
6. 使用真实 MySQL 集成测试、并发测试、故障注入和性能基线验证语义；记录测试环境和原始结果，不把目标当成结论。

### 设计边界

- **原子创建**来自 MySQL 事务语义：事务提交则业务数据和任务行同时存在，回滚则同时不存在。GoRangeTask 的 API 让调用方可以复用这项能力。
- **执行恢复**来自 Worker、租约和重试机制：Worker 崩溃后，任务可以在租约过期后重新尝试。
- **Fencing 的范围**是 GoRangeTask 任务行的状态更新，不会自动撤销旧 Handler 已经写入的业务副作用。
- **Handler 成功不是队列可无条件保证的结果**：永久错误、外部服务长期不可用或最大尝试次数耗尽时，任务会进入死信，需要告警或人工处理。
- **RabbitMQ 保持自身生态位**：需要广播、路由、跨服务/语言订阅的领域事件仍适合 Outbox + RabbitMQ；GoRangeTask 不承担“任务先入库、再转发到 MQ”的中继职责。

## R｜Result：如何证明 GoRangeTask 值得做

GoRangeTask 尚未实现，以下均为验收目标。完成后只将实测结果写入简历。

### 正确性与恢复证据

- 在真实 MySQL 测试中验证事务提交/回滚：提交的业务记录都有对应任务，回滚的业务记录不留任务。
- N 个 Worker 并发领取 M 个任务时，同一有效租约期内每条任务只有一个有效持有者。
- Worker 在领取后崩溃，任务在租约到期后能重新领取；恢复时间有明确统计口径。
- 在旧 Worker 延迟苏醒的场景中，旧 fencing token 的续租、成功写回和失败写回均被拒绝。
- 在 Handler 副作用完成、任务成功状态写回之前杀掉 Worker，确认任务会重复尝试，并用幂等示例证明最终业务状态正确。
- 临时失败按重试策略恢复；永久失败和达到次数上限的任务进入死信且可观测。

事务完整率口径是验证事务集成是否正确的基础检查：

```text
事务完整率 = 已提交业务记录中存在对应任务的记录数 ÷ 已提交业务记录总数
```

在 10,000 笔包含提交和回滚的事务中，目标是已提交记录均有对应任务、回滚事务不残留任务。这个结果证明事务集成正确，**本身不证明 GoRangeTask 比直接 SQL 更强**。（2026-10-17 实测：10,000 笔、8 个并发调用方，完整率 100.00%，回滚残留 0、孤儿任务 0，见性能基线 §8。）

### 性能与项目价值证据

使用固定 MySQL 资源、payload、Worker 数和连接池配置，记录：

- 任务入队对调用方事务/API p50、p95、p99 的额外开销。
- 从事务提交到 Handler 开始的排队延迟，以及 Handler 处理耗时。
- 不同 Worker 并发数下的 tasks/s、积压排空时间和空队列轮询 QPS。
- MySQL CPU、连接池占用、claim 查询计划、锁等待和租约回收耗时。
- 故障恢复后任务的最终状态分布：成功、重试中、死信；明确区分“被尝试执行”与“业务处理成功”。

这些指标用于说明实现是否正确、适用规模和资源成本，不预设 GoRangeTask 比直接 SQL 或 RabbitMQ 吞吐更高。**实测结果见[性能基线](./GoRangeTask-性能基线.md)**——那里同时记录了重复性波动与"测不出来"的项（例如事务内入队的边际成本）。若做方案对照，必须使用相同工作负载；与 RabbitMQ 对照时应采用 Outbox 可靠投递作为基线。

### 完成后使用的 STAR 简历草稿

**S｜情境**  
Go 后端服务需要执行与业务数据相关的后台任务。事务内插入任务记录可以解决业务数据与任务意图的原子创建，但任务领取、并发控制、Worker 崩溃恢复、租约过期、失败重试和旧执行者写回仍需额外实现，容易在不同服务中重复造轮子。

**T｜任务**  
设计并实现 GoRangeTask，一个基于 MySQL 的可嵌入 Go 任务队列。调用方可以在已有事务中创建任务；GoRangeTask 负责任务的并发领取、租约、故障恢复、重试和死信，并明确采用至少一次尝试语义。

**A｜行动**  
实现事务入队 API、MySQL `SKIP LOCKED` 领取、数据库时间租约、续期、递增 fencing token、租约失效后的 context cancel、退避重试和死信。通过独立示例、真实 MySQL 集成测试、并发测试与故障注入验证事务回滚、崩溃恢复、重复执行和旧 Worker 写回拒绝。

**R｜结果**  
实测环境：Intel Core i5-8200Y 4 逻辑核 / 16 GB / go1.27.0；MySQL 8.0.46 容器与压测进程**同机**（`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`）。命令、原始 JSON 与逐项解读见[性能基线](./GoRangeTask-性能基线.md)。

- **事务完整性**：10,000 笔「业务行 + 任务行同一事务」的混合负载（8 个并发调用方，5,000 提交 / 5,000 回滚）⇒ 事务完整率 **100.00%**：已提交的 5,000 行业务记录**全部**有对应任务，回滚后残留业务行 **0**、孤儿任务 **0**。
- **崩溃恢复**：Worker 停止续租后 **2.07 s** 任务由另一个 Worker 接手跑完（租约 2 s / 回收周期 250 ms / 轮询 250 ms，可解释上界 2.53 s）；最终 `attempt = 2`，两个 Worker 的 Handler 各执行 1 次。
- **旧执行者写回**：解冻后的陈旧 epoch 写回被条件更新拒绝（故障注入 **1/1**，`ErrLeaseLost`，整行快照零改动）。样本量为 1，只能说明机制有效，不能当作比率。
- **吞吐**：256 B payload，W=1/4/16 = **24–29 / 47–49 / 66–96 task/s**（两次运行）。4 倍 Worker 只换来 1.4–1.9 倍吞吐，瓶颈在热点索引页争用与 MySQL CPU，不在行锁（行锁等待为 0）。
- **排队延迟**：稳态（队列不积压）p95 = **260–500 ms**，由 250 ms 轮询间隔与空队列退避决定，与任务处理无关（Handler 0.03 ms）；人为积压 1000 条时 p95 是 15–68 s——那是积压的度量，不是调度开销。
- **数据库成本**：每任务固定 **6 条 SQL**、与并发无关（1000 条任务 → 6004–6049 条语句）；InnoDB 行锁等待 **0**（18 个场景×运行组合中 4 个各 1 次、累计 ≤8 ms）；连接池占用等于 Worker 数、等待 0 次；空队列每 worker **≈2 条 SQL/s**。
- **必须说清的边界**：语义是"至少一次**尝试**"，不是"保证业务处理成功"，Handler 必须幂等。吞吐与延迟来自一台同时跑着别的负载的笔记本，同一格两次运行能差 45%，因此这些数字只说明量级与瓶颈位置，不构成对任何目标的承诺。

### 简历压缩版（完成并验证后使用）

> 使用 Go 实现基于 MySQL 的可嵌入任务队列，支持调用方事务内入队与多 Worker 并发领取（`FOR UPDATE SKIP LOCKED`）；以数据库时钟租约、心跳续期与递增 fencing token 实现崩溃恢复和旧执行者隔离，配合指数退避重试与死信管理任务生命周期。以真实 MySQL 集成测试、`SIGSTOP` 进程冻结故障注入和性能基线验证：**1 万笔混合事务事务完整率 100%、崩溃恢复 2.07 s、陈旧写回被 fencing 拒绝（1/1）、单机 4 核 24–96 task/s**。

R 段与简历压缩版中的数字均为 2026-10-17 实测，可追溯到 `bench/results/*.json`；详细需求、技术实现与实测方法分别见《GoRangeTask-需求文档.md》《GoRangeTask-技术设计.md》《GoRangeTask-性能基线.md》。**对外表述以实测为准：不得把"至少一次尝试"写成"保证成功"，不得把单次运行的吞吐写成承诺，也不得把样本量为 1 的故障注入写成比率。**
