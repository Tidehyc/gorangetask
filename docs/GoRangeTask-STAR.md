# GoRangeTask 项目构想：STAR 说明

> 项目名：GoRangeTask（仓库名：`gorangetask`）。
> 文档定位：项目背景与简历叙述，不是实现规格。  
> 状态：立项讨论稿 v0.6。GoRangeTask 尚未实现；行动为计划，结果为待验证目标。  
> 需求、接口、数据模型和验收细节见《GoRangeTask-需求文档.md》。

## S｜Situation：问题从哪里来

在 Go 后端服务中，业务数据变更经常会触发延迟处理、文件/媒体处理、索引构建或补偿工作。若业务数据写入数据库后，再独立向队列投递任务，两步之间可能因进程退出或网络故障而不一致；而 RabbitMQ 这类 Broker 更适合事件路由、广播、削峰和独立消费者，未必是所有同库本地任务的最简执行方式。

Outbox（发件箱模式）把业务变更和待发布事件写进同一个数据库事务，再由投递器把事件交给 RabbitMQ。它解决可靠交接问题，并保留 Broker 的路由、缓冲和消费者解耦能力。GoRangeTask 借由此前对 GCFeed 不同版本及其 Outbox/RabbitMQ 链路的分析获得了问题背景，但项目定位独立于 GCFeed：它要验证的是 Go 服务如何把业务事务与本地后台任务原子绑定，并可靠执行任务。

GoRangeTask 将数据库任务表作为持久化投递通道：调用方在业务事务中写业务数据和任务记录；事务提交后，Worker 从表中领取任务并直接运行 Handler。RabbitMQ 仍适用于需要跨服务/语言分发、广播、Broker 缓冲或独立订阅的领域事件。GoRangeTask 与 Outbox 都可以在事务中记录待处理意图，但前者进一步负责本地 Handler 的领取、租约、重试和执行生命周期。

### 术语解释

- **STAR**：Situation（情境）、Task（任务）、Action（行动）、Result（结果）的项目经历组织方式。
- **MVP**：Minimum Viable Product，最小可验证版本，只实现检验核心设计所需的功能。
- **Producer**：创建任务的业务代码。
- **Worker**：后台进程，从 GoRangeTask 数据库队列领取任务。
- **Handler**：Worker 调用的任务处理函数。
- **Broker**：消息代理，例如 RabbitMQ，负责接收、缓冲、路由和分发消息。
- **幂等**：同一任务重复处理，业务最终效果仍与处理一次相同。
- **至少一次执行**：进程崩溃后任务可重试，因此 Handler 可能重复调用；不保证外部副作用恰好发生一次。

## T｜Task：GoRangeTask 要解决什么

设计并实现 GoRangeTask：一个基于关系型数据库的事务型 Go 任务队列，确保业务数据变更与本地后台任务请求在同一个数据库事务中提交或回滚，并将已提交任务可靠交付给 Worker 执行。

GoRangeTask 要解决两段问题：

1. **原子创建**：业务事务提交时任务一定存在，事务回滚时任务一定不存在。
2. **可靠执行**：Worker 并发领取任务；Worker 崩溃后可恢复；失败时按策略重试；租约失效的旧 Worker 不能覆盖新状态。

GoRangeTask 的保证是“任务记录持久化并至少一次交给 Handler 尝试执行”。它不保证外部操作恰好一次；Handler 必须能处理重复调用。若 Handler 又把消息发送给 RabbitMQ，GoRangeTask 不会自动保证 GoRangeTask 状态与 RabbitMQ 投递的原子性。

| 维度 | GoRangeTask | Outbox + RabbitMQ |
|---|---|---|
| 核心对象 | 本服务要执行的 Job（后台任务） | 要发布给订阅者的领域 Event（领域事件） |
| 事务内记录 | 业务数据 + 可执行任务 | 业务数据 + 待发布事件 |
| 投递路径 | 数据库任务表 → GoRangeTask Worker → 本地 Handler | Outbox → RabbitMQ → 一个或多个消费者 |
| 主要能力 | 事务入队、领取、租约、延迟、重试、恢复、死信 | 可靠交接、路由、广播、Broker 缓冲与跨服务消费 |
| 适用边界 | 生产者和 Handler 同服务、共用数据库 | 需要独立消费者、跨服务/语言分发或 Broker 削峰 |

因此，GoRangeTask 不是泛化的 Cron/清理调度器，也不只是 Outbox 转发器；它是**使用数据库作为本地任务投递通道的任务队列**。当同服务内的任务与业务提交存在原子性要求时，事务入队就是核心价值。

## A｜Action：计划如何实现

详细需求写在《GoRangeTask-需求文档.md》，此处保留高层行动：

1. 选择一种关系型数据库，设计业务事务可调用的 `EnqueueTx`，使任务行使用调用方的同一事务。
2. 实现多 Worker 原子领取、租约续期和过期回收；使用递增租约代次拒绝旧 Worker 状态写回。
3. 实现 Handler 注册、失败重试、退避、死信、幂等键与优雅停机，明确至少一次语义。
4. 用真实数据库进行并发和故障注入测试，验证事务提交/回滚、任务恢复、旧 Worker 写回拒绝和重复处理。
5. 提供独立示例服务和可复现故障实验，作为端到端验证主线；GCFeed 集成只作为 MVP 后的可选案例。

## R｜Result：如何证明 GoRangeTask 值得做

当前没有实现或实验数据。以下是验收目标，完成后再以实测结果作为简历证据。

### 正确性证据

- 对 `[N]` 次业务事务进行提交、回滚和 API/Worker 故障注入：提交的业务记录均有对应任务，回滚的记录没有任务。
- 多 Worker 并发领取时，同一租约期内每条任务只有一个有效持有者。
- Worker 崩溃后，任务在租约过期与恢复扫描后可重新领取。
- 旧租约代次不能续租或写回成功/失败状态。
- 重复执行 Handler 时，幂等业务效果只产生一次。

任务原子创建率的统计口径：

```text
原子创建率 = 已提交业务记录中存在对应任务的记录数 ÷ 已提交业务记录总数
```

首轮目标是在 10,000 次事务（包含回滚及故障注入）中，原子创建率为 100%，且回滚事务不留任务。这个数字是目标，不是现有结果。

### 性能证据

在同样数据库资源、任务参数和并发配置下记录：

- 业务 API 的 p50/p95/p99 延迟，以及事务内额外插入任务的开销。
- 任务从事务提交到 Worker 开始处理的延迟。
- 每秒处理任务数和积压后的排空时间。
- MySQL CPU、连接池占用、领取查询耗时、锁等待和空队列轮询 QPS。

性能基线首先测 GoRangeTask 自身的入队开销、任务延迟、吞吐和数据库负载。若未来与 RabbitMQ 对照，需保持工作负载和消费者拓扑一致，并使用 Outbox 作为可靠基线；不预设 GoRangeTask 吞吐更高。

### 完成后使用的 STAR 简历草稿

**S｜情境**  
多个 Go 服务都可能需要在业务事务中可靠创建后台任务，并由 Worker 执行、重试与恢复。现成消息代理适合领域事件分发和跨服务解耦，但未必是同库事务内本地任务的合适执行模型。GoRangeTask 的问题和验收应独立于某一个业务项目。

**T｜任务**  
设计并实现 GoRangeTask，一个基于 MySQL 的可嵌入 Go 任务队列，使调用方业务数据与后台任务能在同一事务中提交，并让本地 Worker 可靠执行、在故障后恢复。用独立示例和可复现实验验证通用能力；不把替换 RabbitMQ 或接入某个业务项目设为目标。

**A｜行动**  
实现事务内入队、多 Worker 原子领取、数据库时间租约、续租、递增租约代次（fencing token，拒绝过期执行者写回）、租约丢失时取消 Handler context、退避重试和死信。用独立示例 Handler、真实 MySQL 集成测试、并发测试和进程故障注入验证提交、回滚、恢复和旧租约写回拒绝。
