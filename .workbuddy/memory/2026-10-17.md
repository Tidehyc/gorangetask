### 本次实测的关键数字（详见 docs/GoRangeTask-性能基线.md）

- 事务完整率 **100.00%**（10,000 笔、8 并发、5,000 提交 / 5,000 回滚；回滚残留 0、孤儿任务 0）。

  上界 2.53 s；`attempt=2`；两个 Handler 各 1 次；陈旧写回被拒）。
- 吞吐 256 B：W=1/4/16 = 24–29 / 47–49 / 66–96 task/s（两次运行）。
- 每任务固定 **6 条 SQL**（BEGIN+SELECT FOR UPDATE SKIP LOCKED+UPDATE+COMMIT + 回读 + 写回），
  与并发无关（6004 / 6013 / 6047）。

- 空队列每 worker ≈2 条 SQL/s（1.93 / 2.03 / 1.98 QPS；一次空轮询 3 条语句）。
- 稳态排队 p95 = 260–500 ms，**由 250 ms 轮询 + 退避决定，加 Worker 也不降**。
- **测不出**：事务内入队的边际成本，两次运行给 +3.3 ms 与 +30.5 ms（吞吐 −4.4% / −43.8%）。
  结论写"本机噪声内测不出"，不挑数字。

### 踩到的坑（值得记住）

1. **`go build -o <正在运行的二进制路径>` 会打断前台那个进程**。当时以为第三轮被杀了，
   其实是 `-o` 覆盖了可执行文件；后来它其实跑完了（exit=0），我查得太早。**教训：长跑任务
   期间用另一个输出路径**（本次后续改用 `bench-run5`）。
2. **串行跑事务完整性太慢**：本机 fsync 下单笔 `COMMIT` 约 100 ms，10,000 笔要 19 分钟。
   改成 8 个并发调用方 → 67 s、149 笔/s。并发不改变口径，反而更接近真实 API 负载。
3. **排队延迟必须分两种量**：drain 场景的 `queue_wait` p95 是积压的度量（15–68 s），
   不是调度开销；要看调度必须让队列不积压（按固定间隔入队）→ 260–500 ms。
4. **两次运行结论可能相反**：32 KB 下 W=4→16 一次 35.5→36.9（几乎无增益），一次 26.1→50.0
   （接近翻倍）⇒ 该格噪声超过效应，文档如实写"收益不稳定"，不据此下结论。
5. 进度跟踪 §4 表格里有一处未转义的 `||`（在反引号里也一样会拆单元格），已转义为 `\|\|`。
6. `git commit -m "…`||`…"` 会被 shell 当命令替换吃掉反引号内容 ⇒ 提交信息用 `-F 文件`。
