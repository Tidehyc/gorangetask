## §4 第 1+2 项完成（feat `7d09e27` / docs `20552e9`）

### 动手前发现的交互（决定了必须合并做）

`process()` 原先用同一个 `ctx.Err() != nil` 判"停机"，上报文案写死
`"shutdown in progress"`。心跳一旦因**失租**取消 ctx，会走进同一分支并**被报成停机**。
两个原因语义完全不同（停机不写回但成功仍确认；失租什么都不能写），必须分开。

⇒ 改用 `context.WithCancelCause`，三种取消原因各自可辨：

| 原因 | `context.Cause(hctx)` | Worker 处理 |
|---|---|---|
| 停机 | `context.Canceled` | 停止续租、**不释放租约**；失败不写回、成功仍确认 |
| 逐任务超时 | `context.DeadlineExceeded` | 普通失败，走重试/死信 |
| 失去租约 | `ErrLeaseLost` | **任何状态都不写回**，保持 running 交给回收器 |

Handler 也能用 `context.Cause` 分辨自己被谁叫停（`WithTimeout` 的 timerCtx 内嵌
cancelCtx，父取消会把 cause 透传下去；first-cancel-wins 保证 `defer cancel()` 不覆盖）。

### 关键取舍

- **新的 `lease_until` 从数据库当前时间起算，不在旧值上累加**：累加会让租约随续租
  次数越推越远，一次失败的续租就能把任务锁住远超预期。真库用例用**区间断言**排除
  累加实现（两种算法结果相差整整一个原始租约长度）。
- **续租的 `WHERE` 与三条写回完全一致（含 `status='running'`）**：否则失去租约的旧
  Worker 能靠续租把自己"续"回有效状态，fencing 形同虚设；终态任务也不能被续租复活。
- **续租失败 ≠ 失租**：只有 `ErrLeaseLost` 才取消 Handler；驱动错误只上报、下个周期
  重试（需求 §9）。否则一次数据库抖动会掐掉所有在途 Handler。
- **先停看护、等它退出，再写回**：反过来的话续租会在任务写成终态之后到达，因
  status 不再是 running 而返回 `ErrLeaseLost`，把正常结束的任务报成失租。
- **单次续租自带一个心跳周期的超时预算**：数据库卡住时看护协程不能无限期阻塞，
  否则 Handler 返回后的收尾（等看护退出）会一起卡住。
- 停机时**停止续租但不释放租约**（§4.6），租约自然过期后交给回收器。
- 删掉看护里"续租与 stop 撞在一起就不再上报"的守卫：它唯一作用是**吞掉**一条真实
  的续租失败；停机打断的续租已由 `ctx.Err()` 单独挡掉。少一个分支、少一处死角。

# §4 第 3 项：过期租约回收（回收器）

用户说「可以」后开工。这是 §3 留下的缺口的闭合点：停机超时、进程崩溃、失租遗留的
`running` 任务此前**无人接手**。

## 三个形态决定（都取「贴着现有结构」的选项，用户已确认）

1. 能力挂在既有 `WorkerStore` 接口上，不另起可选接口——回收是 Worker 的职责之一。
2. `Config` 只加 `ReapInterval`（默认 30s，**负值关闭**）；批大小做成内部常量
   `reapBatchSize = 100`，不进配置。
3. 被回收行的 `last_error` 用固定文案（`lease expired` / `lease expired at final attempt`），
   不拼接原错误——回收器手上没有别的信息。

## 顺带抓到一个**真 bug**（本次最大的产出）

写并发回归用例时先发现「12 条任务、4 个回收器并发，合计只回收 3 条」，一度以为是
用例设计问题（`limit` 取小了）。把并发路径逐步骤打点后确认 **3 个回收器的 `SELECT`
返回 0 行**；再下沉到 SQL 层用 `performance_schema.data_locks` 定案：

- 回收的加锁读要连带取 `attempt` / `max_attempts`，两列**不在 `ix_gotask_lease` 里**
  ⇒ 不是覆盖索引；优化器于是选 `type=ALL, key=NULL, Using filesort`（全表扫描 + 排序）。
- `FOR UPDATE` 在扫描过程中把**整个积压**锁住：`LIMIT 3` 实际锁了 PRIMARY 上全部 12 行
  （`data_locks` 13 条）；第二个事务执行同一条读返回 **0 行**，却同样把
  `ix_gotask_lease` 上 12 条索引项全锁一遍。
- ⇒ `LIMIT` 不再限制加锁范围，`SKIP LOCKED` 失去意义，并发回收器互相挡住。
- 修复：`FORCE INDEX (ix_gotask_lease)`（锁 13 → 7 条）。**完全确定性复现**，可做回归用例。
- 对照检查：claim 的加锁读**只取 `id`**，对 `ix_gotask_claim` 天然覆盖（实测
  `key=ix_gotask_claim, Using index`、锁 7 条），所以那边无需提示——差异的根源就是
  回收器"不得不多取两列"。

教训（已写进 `MEMORY.md` 红线）：**加锁读要停在预期二级索引上；一旦因为要取索引外的列
而不再是覆盖索引，就用 `FORCE INDEX` 把计划钉死**，并把 `EXPLAIN` 的 `key` + 一次
并发加锁读做成回归用例，别把加锁范围交给优化器。
