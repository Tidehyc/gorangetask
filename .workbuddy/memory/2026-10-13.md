## 开工前确认（用户三选一，均取推荐项）—— 决定「永久失败」怎么表达

进入 §3 Worker 执行闭环第一项「Handler 注册与 payload 解码」前，和用户确认三件事：

1. **永久失败用 `Permanent(err)` 包装函数**，而不是新增要 `%w` 包装的公开哨兵错误。
   理由：调用方只需记住 `Permanent`/`IsPermanent` 两个函数，不会因为漏包一层就把
   「重试没意义」的失败当成可重试错误，白白重试到次数耗尽。
2. **库提供 `TypedHandler[T]` 泛型适配器，让解码失败由库自己兜住**（不是靠调用方自觉）。
   payload 是入队时就固定下来的值，解不出来 ⇒ 重试也不会好。
3. **未知 task type 直接进 dead**（对齐技术设计 §6）：task_type 同样是入队时定死的。

## 实现（提交 e2c4147 + 文档 6a7a5ae）

- `errors.go`：新增私有类型 `permanentError{err}`（`Error()` + `Unwrap()`），
  `Permanent(err) error`（**nil 安全** → 返回 nil，所以 Handler 里写
  `return gorangetask.Permanent(err)` 不会把成功当失败；重复标记也安全）、
  `IsPermanent(err) bool`（用 `errors.As`，可穿透多层 `%w`）。
  用私有类型而非公开哨兵，是为了让「漏包一层」这个错误不可能发生。
- `handler.go`：
  - `Registry.Resolve(taskType) (Handler, error)`：与 `Lookup` 的唯一区别是错误分类——
    未注册类型返回**带永久标记**的 `ErrNoHandler`（仍可 `errors.Is(err, ErrNoHandler)`）。
    `Lookup` 保持不打标记（它只回答「能不能查到」，不替调用方决定任务命运）。
  - `TypedHandler[T any](fn func(ctx, payload T) error) Handler`：内部 `json.Unmarshal`，
    失败返回 `Permanent(fmt.Errorf("%w: cannot decode payload: %w", ErrInvalidPayload, err))`；
    `fn == nil` 在**构造期 panic**（启动配置错误应尽早暴露，而不是变成一次任务失败）。
- 测试：新增 `errors_test.go`（Permanent/IsPermanent/错误链/消息），
  `handler_test.go` 补 `TestRegistryResolve`、5 类畸形 payload、
  null 解码为零值仍正常调用、nil 函数 panic、错误穿透等。
- 验证：`gofmt -l` 空、`go vet ./...` 干净、**根包覆盖率 100%**、`go test ./...` 全绿。
- 《进度跟踪》§3 第一行标记完成（含证据与提交号）。

## §3 第二项「单 Worker claim/execute/ack」已落地（提交 4abcf9b + 7b86355 + 613a142）

开工前和用户确认三点（前两项取推荐项）：
1. **失败写回「闭环且最简」**：成功→succeeded；失败→立即回 pending（delay=0），
   attempt 达上限→dead。退避抖动与永久错误分类留给 §4。
   ⇒ 因此本项的 `Registry.Resolve` 虽返回带永久标记的 `ErrNoHandler`，Worker 暂时
   仍按可重试处理（未知类型会重试到次数耗尽才进 dead），有专门单测固化这个边界。
2. **含 Run 循环 + 并发池**：按 `Config.Concurrency` 起等量 goroutine。
3. **逐任务超时先用 Worker 默认值，后续加列**（用户原话「1,后续加列」）。

结构决策：
- 根包新增 `worker.go`：导出接口 `WorkerStore`（`Claim`/`Succeed`/`Retry`/`MarkDead`）
  + `ClaimSpec` + `ClaimedTask`（带 `Owner`/`Epoch` 作为 fencing 凭据）+ `Worker`。
  **根包只依赖接口不写 SQL**，`store/mysql.Client` 同时实现 `Client` 与 `WorkerStore`
  （加了第二个编译期断言）。这符合技术设计 §7「根包通过接口依赖 store」。
- `store/mysql/worker.go`：Claim 两段式 + 三条写回 SQL。

claim 的两段式（**照技术设计 §5.2 实现，未偏离**）：
1. 事务内 `SELECT id ... FOR UPDATE SKIP LOCKED`——**只取 id**，为的是让加锁读停在
   覆盖索引 `ix_gotask_claim` 上（把 payload 一起取出来覆盖索引就失效了）。
2. 逐条条件更新为 running：置 `lease_owner`/`lease_until`、`lease_epoch+1`、
   `attempt+1`；影响行数 != 1 就回滚整个 claim 事务。
3. **提交之后**才按主键回读整行交给 Worker ⇒ Handler 绝不在事务/行锁内运行。
   崩溃窗口（提交后、回读前挂掉）留给 §4 的回收器，代码注释里写明了。

fencing 语义（后续所有写回都靠它）：`lease_epoch` 每次领取 +1、永不由任务重置；
三条写回 SQL 共用 `(id, status='running', lease_owner=?, lease_epoch=?, lease_until > UTC_TIMESTAMP(6))`
四重条件，影响 0 行 → `ErrLeaseLost`，**不做无条件更新补救**。

值得留下的两个判断：
- **"数据库不可用" ≠ "租约丢失"**：写回遇到驱动错误必须原样冒泡，不能被当成
  `ErrLeaseLost` 咽掉（那会把一次 DB 抖动伪装成"任务已被别人接手"）。有专门用例。
- 端到端用例用**另一条连接**在 Handler 内读库，断言看到的状态已是 `running`——
  这是"claim 事务先提交"的唯一直接证据，比任何注释都硬。

worker.go 里**唯一没有公开出口的是基础设施错误**：`w.onError` 是留给测试的内部
缝隙，默认丢弃。日志出口属于 §5「结构化日志」，本项刻意不加公开 API（怕擅自
扩公开面）。⇒ 已知局限，下轮可跟用户确认是否加 `WithErrorHandler`。

本项没有覆盖的（都在 Worker 的 doc comment 里逐条列了）：租约续期 ⇒ **Handler 必须
能在 LeaseDuration 内跑完**，否则租约过期、写回被 fencing 拒绝，任务要等 §4 的回收器；
无回收器 ⇒ 崩溃留下的 running 任务无人接手；无 panic 隔离；ctx 取消不等待在途 Handler。

测试：根包 22 个单测（内存假 store，覆盖率 100%；并发池用「Handler 内栅栏」证明
确有 N 个同时进入）+ store/mysql 21 个真库用例。全量 `go test -race ./...`
**236 条记录（116 顶层 + 120 子用例）、0 FAIL、0 SKIP**；store/mysql 93.1%。

## §3 第三项「多 Worker 并发领取」完成（提交 454ccac + 文档 d9e784f）

用户说「先按序号完成3」= 按序号来，先做 §3 第三行（不跳到 §4）。

**本项不需要改生产代码**——claim 从设计上就是并发安全的（`FOR UPDATE SKIP LOCKED`
+ 单条 `WHERE status='pending'` 条件更新）。产出是三个真库用例，把"看起来对"变成"被证明"：

1. `TestConcurrentClaimNeverDoubleClaims`：8 个领取者同一 barrier 后抢 40 条任务，
   各用不同 `Limit`（1..5，顺带覆盖批量领取路径）。**两层断言**：
   - 进程侧：拿到的 id 两两不重复、零丢失；
   - **库侧独立复核**：每条任务的 `lease_epoch`/`attempt` 全是 1。
   第二层是关键——它不依赖进程侧自己的记录，进程侧代码写错了也照样抓得住。
   实测分布 `worker-0:2 worker-1:4 worker-2:6 worker-3:8 worker-4:8 worker-5:2
   worker-6:4 worker-7:6`（8 个 owner 全参与，合计 40），确认是真并发。
   分布只用 `t.Logf` 记录、**不做断言**——断言会依赖 goroutine 调度时序而变 flaky。
2. `TestClaimSkipsRowsLockedByAnotherSession`：另一条连接用**普通 `FOR UPDATE`**
   锁住"本该第一个被领走"的行，Claim 必须跳过它、拿走其余两条且不阻塞（断言 <3s），
   锁释放后那条仍可领取。这是 `SKIP LOCKED` 语义的直接验证，也是多 Worker 能并行
   领取的前提（没有它，抢占就退化成一串串行等待）。
3. `TestMultipleWorkersProcessEachTaskExactlyOnce`：4 个 Worker 实例（各 2 并发，
   即 8 个并发领取协程）跑 24 条任务，断言每条 Handler **恰好执行 1 次**。

## §3 第 4 项：Worker graceful shutdown（提交 `6fc14d7` / 文档 `d6bf412`）

需求文档 §4.6 的三条要求：停止领取新任务、向运行中的 Handler 发 cancel、
在 shutdown timeout 内等待退出；**未能确认 Handler 已停止时不提前释放租约**。

### 动手前的现状盘点（三项缺陷）

1. `Run` 是裸 `wg.Wait()`：不理会 ctx 的 Handler 能把 `Run` **永久卡死**。
2. Handler 因停机被取消后返回的错误走了 `fail()` → **写回 pending**。这违反 §4.6：
   另一个 Worker 会在旧副作用可能仍在途时立刻重跑。
   注意这个 bug 在真库上**是隐性的**——`Retry` 用的是已取消的 ctx，UPDATE 本身就
   失败了，任务"看起来"留在 running。是**错误的原因**保住了正确的结果。所以
   只在真库断言"停机后仍 running"**抓不住**它；必须用根包的内存 store 断言
   "根本没调用 Retry"。
3. 停机期间 Handler 若**成功返回**，`Succeed(ctx)` 会因 ctx 已取消而写不回去，
   白白多执行一次。

### 实现要点

- **有界等待**：`Run` 把 `wg.Wait()` 挪进独立 goroutine 收口到 `loopsDone`，
  等 `<-ctx.Done()` 后 `select { loopsDone / ShutdownTimeout 定时器 }`，超时返回
  新增哨兵 **`ErrShutdownTimeout`**（生命周期信号，不是任务失败）。顺手删掉了
  第一个 `select` 里 `<-loopsDone` 的分支：循环只会在 ctx 取消后退出，该分支
  实际不可达，留着就是一条永远 0 覆盖的死代码（覆盖率从 100% 掉到 99.7% 时才
  发现）。
- **停机不写回失败，但确认成功**：判据是 `ctx.Err() != nil`。
  - `err != nil` → 只 `report`，任务保持 running 等租约过期（回收器 §4 接手）；
  - `err == nil` → 仍然 `Succeed`，但换用
    `context.WithTimeout(context.WithoutCancel(ctx), ShutdownTimeout)`。这样已经
    干完的活不会被停机连带丢掉，同时写回本身仍受预算约束。
- **批内停机**：`runOnce` 逐条处理前先看 `ctx.Err()`，已取消就不再启动剩余 Handler
  （启动了也是立刻被取消，等于领出来又扔掉），一次性 report 剩余条数。
- Worker 文档注释里"尚未实现的语义"清单同步更新：优雅停机移出，并明确写下
  "租约丢失不会取消 Handler（它只观察停机取消）"这一区别。

### 测试（根包 4 个 + 真库 1 个）

- `TestWorkerShutdownCancelsInFlightHandlerAndDoesNotWriteBack`：断言取消确实传到
  Handler（`sawCancel` 收到 `context.Canceled`）、`Run` 返回 nil、retry/dead/succeed
  三个写回**全为 0**。
- `TestWorkerShutdownTimeoutAbandonsStuckHandler`：Handler 故意无视 ctx，断言
  `Run` 返回 `ErrShutdownTimeout`，且耗时**不少于** `ShutdownTimeout`（顺带证明它
  没有提前放弃）。用例结束用 `t.Cleanup` 放走泄漏的 goroutine。
- `TestWorkerShutdownAcksHandlerThatFinishedInTime`：内存 store 新增 **`honourCtx`
  开关**（像真驱动一样在 ctx 已取消时直接失败），证明脱离取消的 context 是必需的。
- `TestWorkerStopsLaunchingHandlersAfterShutdown`：`BatchSize=3` 三条一批，断言
  Handler 只被调用 1 次、整批零写回。
- 真库 `TestShutdownLeavesCancelledTaskRunningForTheReaper`：断言停机后
  `status='running'`、`lease_owner`/`lease_until` 仍在、`lease_epoch` 未变、
  `attempt` 未增加、`last_error` 仍为 NULL。
