## 交付物：`example/basic`（新包）

- `schema.sql`：业务表 `example_orders`（示例自己拥有；库只管 `gotask_tasks`）。
- `order.go`：`Store.CreateOrder` 就是示例的核心——`BeginTx` → `tx.ExecContext` 插订单行
  → **同一个 `tx`** 调 `client.EnqueueTx` → `Commit`。顺序与"为什么"都写在注释里
  （库不开/不提交/不回滚调用方事务；返回的 taskID 在提交前不代表任务已存在）。
  `GetOrder` / `ListOrders` 是读取面。
- `handler.go`：幂等靠**条件更新** `WHERE id = ? AND status = 'pending'`。
  影响 1 行＝首次执行；影响 0 行＝**回读业务状态**区分"已导出"（返回 nil，不是失败）
  与"订单不存在"（`Permanent`）；状态既非 pending 也非 exported ⇒ **可重试**失败
  （防"别的东西动过这行"）。`delay` 用 `timer + select{ctx.Done()}` 实现以便立刻收手。
- `app.go`：`Open`（sql.Open → Ping → Migrate + schema.sql → `mysqlstore.New` →
  Register → `NewWorker`）、`Run`、`Close`。建表顺序刻意写明：**迁移任务表 → 建业务表
  → 构造 store**（store 只读表不建表）。
- `cmd/demo/main.go`：`signal.NotifyContext` 接 Ctrl-C；进度表**只走公开 API**
  （`Store.GetOrder` + `Client.Get`）读；收尾点出仍非终态的任务并提示"租约过期后由回收器
  接手，用 `-orders 0` 再起一个看着它被捡走"。

## 两处被"数字不对"揪出来的问题（本轮最大的收获）

### 1）测试自身的时序缺陷（覆盖率浮动出卖了它）

`TestExampleInterruptedTaskIsRequeuedAfterItsLeaseExpires` 原先靠"库里 `status` 变成
`running`"决定何时停机。claim 提交与 Handler 启动之间**有窗口**：在窗口里停机会让
`runOnce` 按设计跳过整批、**Handler 根本没启动**，而任务仍是 `running`、仍会被回收器
接手——终态一模一样 ⇒ 用例照样通过却什么都没测到。

发现方式：**example 包覆盖率在两个值之间浮动**（73.3% / 77.2%）。低的那次
`ExportOrderHandler` 里 `delay > 0` 那几行一次都没执行。定位手段：
`for i in 1 2 3; do go test -coverprofile=...; done` 再看 `go tool cover -func`
的逐函数数字，以及对比不同 profile 里"非零 branch"的差集。

修法：包一层示例的慢 Handler，**进来就先敲 `entered` 通道**，用例等到这个信号才停机。
连跑 5 次该分支每次都被覆盖，浮动消失、覆盖率稳定在 77.2%。
⇒ 同一个坑**踩了第二次**（§6「claim 后退出」那行已记过一次），写进红线。

### 2）库里 `ack` 的竞态（示例的端到端用例撞出来的）

`TestExampleWorkerExportsOrders` 以约 1/8 的概率报 `task 2 status = "running"`。
不是用例的问题：`process` 判 `ctx.Err() != nil` 时停机**还没开始**，于是 `ack` 用的是
**没脱离取消**的原 ctx；就在这次 DB 往返途中 ctx 被取消 ⇒ 成功结果写不回去。
这直接违背 `ack` 自己注释里的承诺（"已经成功返回的 Handler 仍会尽力确认"）。

诊断手段：`w.onError` 没有公开出口，临时给 `report` 加一行 `fmt.Fprintln(os.Stderr, ...)`
⇒ 拿到原文 `ack success for task 2: succeed task: context canceled`，一次定位。
（诊断补丁用完即还原，`md5` 核对一致。）

修法：`ack` **总是**脱离停机取消（预算仍是 `ShutdownTimeout`，顺带把"数据库卡住"的
等待也变成有界，与续租一致）。回归用例 `TestWorkerAcksSuccessEvenIfShutdownStartsMidAck`
借 fake 的新钩子 `onSucceedEntered` 把停机**确定性地**卡在写回往返正中间；
既有的 `TestWorkerShutdownAcksHandlerThatFinishedInTime` 只覆盖"进来时 ctx 已取消"，
所以旧实现下它照样通过、抓不到这个空白。证伪：改回有条件脱离 ⇒ 新用例报
`succeeded = [], want [61]`，既有那条仍通过。
⇒ 修复后 `TestExampleWorkerExportsOrders` 用 `-cover` 连跑 60 次 0 失败。
