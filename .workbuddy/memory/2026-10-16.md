## 交付物：`example/basic`（新包）

- `schema.sql`：业务表 `example_orders`（示例自己拥有；库只管 `gotask_tasks`）。
- `order.go`：`Store.CreateOrder` 就是示例的核心——`BeginTx` → `tx.ExecContext` 插订单行

  （库不开/不提交/不回滚调用方事务；返回的 taskID 在提交前不代表任务已存在）。
  `GetOrder` / `ListOrders` 是读取面。
- `handler.go`：幂等靠**条件更新** `WHERE id = ? AND status = 'pending'`。
  影响 1 行＝首次执行；影响 0 行＝**回读业务状态**区分"已导出"（返回 nil，不是失败）
  与"订单不存在"（`Permanent`）；状态既非 pending 也非 exported ⇒ **可重试**失败
  （防"别的东西动过这行"）。`delay` 用 `timer + select{ctx.Done()}` 实现以便立刻收手。
- `app.go`：`Open`（sql.Open → Ping → Migrate + schema.sql → `mysqlstore.New` →
  Register → `NewWorker`）、`Run`、`Close`。建表顺序刻意写明：**迁移任务表 → 建业务表
  → 构造 store**（store 只读表不建表）。
- `cmd/demo/main.go`：`signal.NotifyContext` 接 Ctrl-C；进度表**只走公开 API**
  （`Store.GetOrder` + `Client.Get`）读；收尾点出仍非终态的任务并提示"租约过期后由回收器
  接手，用 `-orders 0` 再起一个看着它被捡走"。

## 两处被"数字不对"揪出来的问题（本轮最大的收获）

### 1）测试自身的时序缺陷（覆盖率浮动出卖了它）

`TestExampleInterruptedTaskIsRequeuedAfterItsLeaseExpires` 原先靠"库里 `status` 变成
`running`"决定何时停机。claim 提交与 Handler 启动之间**有窗口**：在窗口里停机会让
`runOnce` 按设计跳过整批、**Handler 根本没启动**，而任务仍是 `running`、仍会被回收器
接手——终态一模一样 ⇒ 用例照样通过却什么都没测到。

发现方式：**example 包覆盖率在两个值之间浮动**（73.3% / 77.2%）。低的那次
`ExportOrderHandler` 里 `delay > 0` 那几行一次都没执行。定位手段：
`for i in 1 2 3; do go test -coverprofile=...; done` 再看 `go tool cover -func`
的逐函数数字，以及对比不同 profile 里"非零 branch"的差集。

修法：包一层示例的慢 Handler，**进来就先敲 `entered` 通道**，用例等到这个信号才停机。
连跑 5 次该分支每次都被覆盖，浮动消失、覆盖率稳定在 77.2%。
⇒ 同一个坑**踩了第二次**（§6「claim 后退出」那行已记过一次），写进红线。

### 2）库里 `ack` 的竞态（示例的端到端用例撞出来的）

`TestExampleWorkerExportsOrders` 以约 1/8 的概率报 `task 2 status = "running"`。
不是用例的问题：`process` 判 `ctx.Err() != nil` 时停机**还没开始**，于是 `ack` 用的是
**没脱离取消**的原 ctx；就在这次 DB 往返途中 ctx 被取消 ⇒ 成功结果写不回去。
这直接违背 `ack` 自己注释里的承诺（"已经成功返回的 Handler 仍会尽力确认"）。

诊断手段：`w.onError` 没有公开出口，临时给 `report` 加一行 `fmt.Fprintln(os.Stderr, ...)`
⇒ 拿到原文 `ack success for task 2: succeed task: context canceled`，一次定位。
（诊断补丁用完即还原，`md5` 核对一致。）

修法：`ack` **总是**脱离停机取消（预算仍是 `ShutdownTimeout`，顺带把"数据库卡住"的
等待也变成有界，与续租一致）。回归用例 `TestWorkerAcksSuccessEvenIfShutdownStartsMidAck`
借 fake 的新钩子 `onSucceedEntered` 把停机**确定性地**卡在写回往返正中间；
既有的 `TestWorkerShutdownAcksHandlerThatFinishedInTime` 只覆盖"进来时 ctx 已取消"，
所以旧实现下它照样通过、抓不到这个空白。证伪：改回有条件脱离 ⇒ 新用例报
`succeeded = [], want [61]`，既有那条仍通过。
⇒ 修复后 `TestExampleWorkerExportsOrders` 用 `-cover` 连跑 60 次 0 失败。

## 追加：demo `-orders 0` 起来 3 秒就自己收工（收尾冒烟时抓到）

`-orders 0` 本该"不建订单、只起 Worker 看着遗留任务被捡走"，实际只跑一次 tick（约 3 秒）
就打印 "all orders exported" 收工——完全起不到观察作用。根因在 `watch`：判定收工的
`allDone` 来自 `printProgress(tracked)`，而 `tracked` 为空时它返回 `allDone=true`，
于是**空集合上"全都完成了"恒真**，第一次 tick 就主动请求停机。

修法：抽纯函数 `stopReason(tracked int, allDone bool) (string, bool)`，对 `tracked == 0`
**永不自动停**（"本次没建订单，'全都完成'是句空话"）；`watch` 里再按 `len(tracked)` 是否
为零分派 `printProgress` / 新增的 `printOrders`。`printOrders` 用 `Store.ListOrders`
平铺业务表——遗留订单不是本进程建的，拿不到任务 ID，而公开 API 只有"按 ID 查任务"、
没有"按队列列举"；好在故障演示关心的正是业务行从 `pending` 变 `exported` 的那一下，
那就是任务确实被接手的证据。`main_test.go` 3 个单测钉住三种取值组合；
证伪：删掉 `tracked == 0` 分支 ⇒ `TestStopReasonNeverStopsWithNothingTracked` 立刻
报 "want no stop"，即证这条判断真的在管用。README 第 203 行注释同步改成
"不建订单，只起 Worker 观察业务表，按 Ctrl-C 结束"。

⇒ 教训：**"全都完成了"这种判据在有"空输入"可能时，先问空输入下它是什么**。
空集合上的全称命题恒真，会把"什么都没做"误判成"都做完了"。

## §5 第 2 项「故障演示」落地（README 可照着重现）

要写的是「停机打断 → 租约过期 → 换个 Worker 接手跑完」。为此给 `cmd/demo` 补了
`-lease` / `-reap` 两个开关（默认 `LeaseDuration 30s` / `ReapInterval 30s`，照默认跑这条
路径要等几十秒，没法写进文档让人照着秒级复现）。

**踩到的不变量**：库要求 `HeartbeatInterval < LeaseDuration`，而默认心跳写死 10s。
只覆盖 `LeaseDuration`、把心跳留给库默认，`-lease 5s` 就会撞上校验 → `NewWorker` 当场
报「heartbeat interval (10s) must be < lease duration (5s)」，第一步命令直接废。
修法：租约被覆盖时心跳按同样的 1/3 比例一并推导，抽成纯函数 `workerConfig(lease, reap)`。
**这个坑值得记住的形态**：一个"只改 A"的旋钮，会因为它与 B 之间存在不变量而必须连 B 一起改。
诀窍是**别只看被改的那个字段，去读校验函数**（`Validate` 里写了谁依赖谁）。

单测 3 条 + 证伪 3 条（全部成立）：去掉心跳推导 ⇒ 报上面那条校验错（原文与我预判一字不差）；
`reap != 0` 改成 `reap > 0` ⇒ 负值透传用例失败；给 `workerConfig` 抄死库默认值 ⇒ 零值用例失败。
零值那条的写法有讲究：**不引用库的默认值常量**，只断言"三个字段都为 0"——引用常量等于
"实现等于它自己"，库改默认值时测试照样绿，等于空断言。

**实测复现（README 那一节就是照这个写的）**：第一幕 `-orders 2 -handler-delay 30s
-lease 5s -reap 2s` 跑 12s 后 SIGINT ⇒ 业务行 `pending`、任务行 `running`、`attempt 1`；
再等 6s 查库 ⇒ `lease_until` 已过去但**状态仍是 `running`**；第二幕 `-orders 0 -lease 5s
-reap 2s` ⇒ 约 2s（一个回收周期）后回收器放回 `pending`、同一 Worker 领取跑完，
收尾 `succeeded / attempt 2`。

⇒ 两个最该记住的点：
1. **租约到期本身不改变任何东西**。没有活着的 Worker 在跑回收器，过期租约只会一直停在
   `running`——"回收只在 Worker 进程内跑"这条边界，在文档里必须写成可观测的现象，而不是
   一句"由回收器接手"。
2. **别把业务表状态当任务状态读**。`-orders 0` 模式打印的是 `printOrders` 的业务表，
   它的 `pending` 意思是"业务行还没被写回"，跟任务在不在排队无关。我一度被这个绕进去，
   以为"1 秒时已 pending"与"回收器 2 秒才跑第一趟"矛盾——其实是两列不同的东西。
   查证手段：`attempt` 从 1 变 2，才是"同一条任务被领过两次"的直接证据。

  这是最需要挡的误用——非事务 `*gorm.DB` 会让任务行走自己的连接，**编译通过、运行不报错，

  「换成非事务 `Enqueue` ⇒ **只有回滚用例失败**，提交用例照常通过」正好演示

### 本轮踩到的坑

1. **超时判据取错了 ctx**：`TestMetricsTimeoutIsCountedAsItsOwnEvent` 一开始按
   `context.Cause(taskCtx)` 判超时，报 `HandlerTimedOut` 零次。真因是超时 deadline 加在
   `execute` **内部的 `runCtx`** 上，`taskCtx` 根本看不到它 ⇒ 改让 `execute` 返回
   `(err, timedOut)`。「这个 ctx 看得见那个 deadline 吗」值得每次都问一遍。
2. **错误类型别靠文案匹配**：`panicError` 从 `fmt.Errorf("handler panicked: ...")` 改成
   具名类型——匹配前缀会在改措辞时静默失效（错误文案逐字未变）。
3. **测试实现也会被 `-race` 抓到并发缺陷**：`recordingLogger.messages` 在锁外读
   `len(records)`。Logger 契约要求实现并发安全，第一个踩到的是测试自己的实现。
4. **`runOnce` 不打基础设施错误日志**（那是 `loop` 的职责）：`TestWorkerLogsInfrastructureError`
   必须走 `w.Run(ctx)` + `waitUntil` 等日志，只调 `runOnce` 就断言拿不到。
